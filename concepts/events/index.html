事件

NautilusTrader 把执行、持仓、账户和时间的变化建模为事件。MessageBus 把这些事件路由给相关组件，并在支持的地方送达策略处理函数。本篇介绍事件类型、它们的分发方式，以及成交与成交更正如何产生持仓事件。

事件类别​

类别示例来源
订单OrderAccepted、OrderFilled、OrderCanceled执行流水线
持仓PositionOpened、PositionAdjusted成交与记账变化
账户AccountStateExecutionClient / Portfolio
时间TimeEventClock（定时器与提醒）

处理函数分发​

事件到达策略时，系统按固定顺序调用处理函数。专用处理函数先于汇总处理函数执行，因此可以任选一种粒度，或两者都用。

策略只在运行期间把事件交给处理函数。启动前或停止后到达的事件不会分发。

Python 数据 actor 不暴露订单事件回调，也不暴露原始消息总线。要把派生值从策略传给数据 actor，使用信号。参见 Actor：订单事件处理。

订单事件​

  1. 专用处理函数（例如 on_order_filled）。
  2. on_order_event（接收全部订单事件）。

持仓事件​

分发给策略的持仓生命周期事件：

  1. 专用处理函数（例如 on_position_opened）。
  2. on_position_event（接收全部分发的持仓生命周期事件）。

时间事件​

定时器和提醒产出 TimeEvent 对象。调用 set_timer 或 set_time_alert 时传入 callback，可把事件定向到自己的方法。

省略 callback 时：

  • 若同名回调此前已注册，则沿用该回调。
  • 否则事件送到 on_time_event。

订单事件​

订单事件负责初始化订单、改变其状态或更正其成交历史。执行流水线先把事件应用到订单和 Cache，再发布到 MessageBus。下表列出主要状态迁移。部分成交、外部和触发式订单还有其他迁移，见完整的订单状态流。

事件主要迁移处理函数
OrderInitialized创建或实化订单on_order_initialized
OrderDeniedInitialized -> Deniedon_order_denied
OrderEmulatedInitialized -> Emulatedon_order_emulated
OrderReleasedEmulated -> Releasedon_order_released
OrderSubmittedInitialized/Released -> Submittedon_order_submitted
OrderAcceptedSubmitted -> Acceptedon_order_accepted
OrderRejectedSubmitted -> Rejectedon_order_rejected
OrderTriggeredAccepted -> Triggeredon_order_triggered
OrderPendingUpdateAccepted -> PendingUpdateon_order_pending_update
OrderPendingCancelAccepted -> PendingCancelon_order_pending_cancel
OrderUpdatedPendingUpdate -> 原状态on_order_updated
OrderModifyRejectedPendingUpdate -> 原状态on_order_modify_rejected
OrderCancelRejectedPendingCancel -> 原状态on_order_cancel_rejected
OrderCanceledPendingCancel/Accepted -> Canceledon_order_canceled
OrderExpiredAccepted -> Expiredon_order_expired
OrderFilledAccepted -> Filled/PartiallyFilledon_order_filled
OrderFillVoided更正已知成交，或对未知成交断言终态on_order_fill_voided

Python 订单事件的公共字段​

每个具体的 Python 订单事件都暴露以下字段：

字段说明
trader_idTrader 实例标识。
strategy_id订单关联的策略。
instrument_id订单所属金融工具。
client_order_id客户端分配的订单标识。
event_id事件唯一标识。
ts_event事件发生时刻的 UNIX 纳秒时间戳。
ts_init事件初始化时刻的 UNIX 纳秒时间戳。
causation_id引发本事件的源事件或报告（若已知）。

各订单事件页面会列出其特有字段。venue_order_id、account_id 和 reconciliation 只在暴露这些字段的 Python 事件类上出现。例如 OrderFilled 额外有 last_qty、last_px、trade_id 和 commission。 OrderFillVoided 标识被更正的那笔成交，并携带其累计作废数量。

持仓事件​

持仓生命周期事件描述由成交和成交更正引起的缓存持仓变化。ExecutionEngine 处理每个 OrderFilled，更新或创建持仓，并发出对应的生命周期事件。

当 OrderFillVoided 更正一笔已本地应用的成交时，引擎会按剩余的有效成交历史重建每个受影响的缓存持仓，不会发出反向成交。发布更正后，若被更正的持仓仍然持有，引擎发出 PositionChanged；若已平掉，则发出 PositionClosed。只涉及订单的更正不产生持仓事件。

事件触发时机处理函数
PositionOpened成交创建了新持仓。on_position_opened
PositionChanged成交或更正改变了持仓中数量。on_position_changed
PositionClosed成交或更正使数量归零。on_position_closed
PositionAdjusted 不会送达任何持仓处理函数

PositionAdjusted 记录常规成交之外的数量或已实现盈亏变化，例如以基础货币计的手续费和资金费。ExecutionEngine 会发布它，但 on_position_event 和任何专用处理函数都收不到。要查看记录的历史，检查 position.adjustments()。

从成交到持仓：因果链​

下图展示单个 OrderFilled 事件如何产生持仓事件，即订单管理与持仓跟踪之间的衔接。

逐步说明：

  1. 成交到达：ExecutionEngine 经执行流水线收到 OrderFilled 事件。
  2. 订单状态：引擎把成交应用到订单对象，并把更新后的订单写回 Cache。
  3. 持仓 ID：引擎根据 OMS 类型和策略配置确定这笔成交归属哪个持仓。
  4. 持仓生命周期：引擎按以下三种方式之一创建或更新持仓：
    • 该 ID 尚无持仓：引擎根据成交创建 Position，加入 Cache，发出 PositionOpened。
    • 持仓存在且成交后仍持有：引擎把成交应用到持仓，更新 Cache，发出 PositionChanged。
    • 持仓存在且被关闭（数量归零）：引擎应用成交，更新 Cache，发出 PositionClosed。
  5. 持仓反转：成交使持仓反向时（例如对 10 手多头卖出 15 手），引擎把成交拆成两部分：一部分平掉原持仓（PositionClosed），另一部分开出新持仓（PositionOpened）。

从订单追溯到持仓​

Cache 提供在订单与持仓之间导航的方法：

# From a position, find all orders that contributed fills
orders = self.cache.orders_for_position(position.id)

# From an order, find the position it belongs to
position = self.cache.position_for_order(order.client_order_id)

# The opening order is stored directly on the position
opening_order_id = position.opening_order_id

账户事件​

AccountState 事件表示余额与保证金快照。触发时机：

  • 交易场所上报账户更新（经执行客户端）。
  • 持仓更新后 Portfolio 重新计算账户状态（针对启用了 calculate_account_state 的保证金账户）。

账户状态包含余额、保证金、账户类型和基础货币。Portfolio 内部订阅这些事件，以维护敞口和余额跟踪。完整字段列表见 AccountState。
