Lighter

Lighter 是面向现货与永续合约的 decentralized central-limit-order-book 交易所（去中心化中央限价订单簿），采用以太坊零知识 rollup 结算，撮合与排序在链下完成。 适配器（adapter）同时支持 Lighter 及其 Robinhood Chain 部署。

nautilus-lighter crate 提供 Rust 数据与执行客户端、类型化的 REST 与 WebSocket 模型，以及一个 内置的 L2 签名器，使用 ECgFp5 上的 Schnorr 签名。本页介绍部署配置、能力与运行限制。

L2 签名基准测试与官方 Go SDK 的对比见 crates/adapters/lighter/benches/BENCHMARKS.md。 绝对耗时因机器而异，只有同一台机器上测得的差值才有意义。

概览​

  • LighterRawHttpClient：面向公共与账户端点的低层 REST 客户端。
  • LighterHttpClient：领域 REST 客户端，把金融工具、成交、K 线、资金费与簿解析为 Nautilus 模型类型，并返回类型化的场所订单与账户负载。
  • LighterWebSocketClient：可重连的 WebSocket 客户端，负责公共行情与私有账户流。
  • LighterDataClient：Nautilus 数据客户端，负责金融工具、成交、报价与 L2 market-by-price （MBP）订单簿。
  • LighterExecutionClient：Nautilus 执行客户端，负责账户流、订单提交、修改、撤销与对账报告。
  • LighterDataClientFactory 与 LighterExecutionClientFactory：live-node 工厂接线。

Python 扩展暴露配置、部署与环境选择、工厂，以及集成方吊销。live 节点通过 Rust trait 使用数据 与执行客户端。

示例​

运行 tester 之前，先编辑其模块级常量，包括 LIGHTER_DEPLOYMENT 与 LIGHTER_ENVIRONMENT。 Rust 与 Python tester 启动后立即连接，这些选择器不读取环境变量。

注意

两个执行 tester 默认都开启下单：Rust 设置 DRY_RUN = false 并选择 Lighter Mainnet；Python 设置 DRY_RUN = False 并选择 Lighter Testnet。在任一主网部署上，已注资的账户会下真实订单。 运行 tester 前先检查金融工具、数量、部署与环境，或开启 DRY_RUN 以只连接不下单。

紧急账户清理​

cargo run --bin lighter-flatten -p nautilus-lighter 提交一次账户级的立即撤销，读取一份持仓 快照，并为快照中的持仓提交 reduce-only 的 immediate-or-cancel（IOC）平仓单。

注意

运行该命令前先停掉该账户的其他写入方。清理作用于整个账户而非单个策略，先看清当前账户与 持仓。

该命令不确认、也不重试请求。成功退出只表示撤销与发现的平仓单已提交且没有已知错误，不代表 账户已平。事后检查账户状态，有残留就重跑。

每次运行最多提交 15 笔平仓：16 个交易的 nonce 窗口中，撤销占用一个槽位。快照不完整、请求 失败或提交失败都会返回错误。平仓流程 15 分钟超时。

把 LIGHTER_DEPLOYMENT 设为 lighter 或 robinhood，LIGHTER_ENVIRONMENT 设为 mainnet 或 testnet。省略选择器时默认 Lighter Mainnet，并选择对应的凭据命名空间。

限制​

  • 原生的 OTO、OCO 与 OTOCO 组合要求或有订单一节描述的形态。Nautilus 的 OUO 关系不受原生组合支持。TWAP 未实现。Lighter 没有移动止损订单类型，也没有冰山显示数量字段。
  • 非或有订单列表、批量修改与显式批量撤销，会把支持的子单自动拆分为每批最多 15 个交易的 WebSocket 批次。原生或有列表使用一个组合交易。
  • CancelAllOrders 在该客户端账户上跨策略撤销缓存的挂单，保留各订单所属策略，并按金融工具与 可选的 order_side 过滤。它按每批最多 15 笔逐单撤销。适配器的原生 cancel-all 模式是账户级 的。Lighter 的 新版签名器增加了市场过滤， 但没有方向过滤。
  • 现货交易支持市价单与限价单。条件止损与止盈订单仅限永续市场。
  • query_account 与持仓报告重放最近缓存的私有 WebSocket 状态。
  • 无范围的订单对账被限定在已配置或已观察到的活跃市场内，避免在标准 REST 配额下向全场所扇出。

符号体系​

Lighter 使用 64 位 market_index。既有市场保留其按区间划分的 ID。 Lighter Mainnet 2026 年 9 月升级与 Robinhood 随后的升级之后，新的现货与永续市场取 4095 及以上的第一个空闲索引。

产品类型永远取自 market_type，绝不从索引推断。适配器从 GET /api/v1/orderBookDetails 加载 映射，并把场所符号转换为 Nautilus InstrumentId。

自定义场所标识​

要在 Lighter 协议端点之间使用不同的 Nautilus 标识，在两个客户端配置上设置 venue。它限定 金融工具、缓存条目、消息主题、socket 状态与执行路由，而不改变部署的协议行为。

为兼容起见，工厂名保持 LIGHTER。ClientId 是客户端注册名。Robinhood 要按 ClientId 路由 时，注册为 LIGHTER_ROBINHOOD。两种语言的示例都由 LIGHTER_DEPLOYMENT 推导它。支持自定义 客户端名。

Nautilus 按 issuer 路由账户命令，因此 account_id 的 issuer 必须与解析出的场所一致： LIGHTER_RH_ALT 需要形如 LIGHTER_RH_ALT-001 的 ID。自定义场所不会启用自定义链 ID 或归因。

账户与 API key 设置​

公共行情不需要账户。私有流与执行需要来自同一部署与环境的账户索引、API key 索引与私钥。 每行各有独立的命名空间：

  1. 打开目标部署的账户页面并登录。生成 API key 之前，先创建或选择交易账户，包括目标子账户。

  2. 按 Lighter 的 账户索引查询， 对着该部署的 REST URL 操作。非 Robinhood Mainnet 的部署，把示例 URL 换成其 部署表取值：

    LIGHTER_SETUP_API_URL="https://api.rh.lighter.xyz"
    LIGHTER_SETUP_L1_ADDRESS="0xYOUR_ETHEREUM_ADDRESS"

    curl -sS --get \
      "${LIGHTER_SETUP_API_URL}/api/v1/accountsByL1Address" \
      --data-urlencode "l1_address=${LIGHTER_SETUP_L1_ADDRESS}"

    从 sub_accounts 中所需条目读取 index。一个钱包可以拥有主账户和若干子账户，每个子账户 有独立的账户索引与 API key。

  3. 在所选账户的 API key 页面选择 Generate API Key。使用 [4, 254] 中未占用的索引。 Lighter 的 API key 文档把 [0, 3] 保留给其 界面，255 是 API 查询哨兵。Robinhood 还保留 157。见 Robinhood API keys。

  4. 关掉弹窗前先保存生成的私钥，Lighter 不会再显示它。

  5. 直接配置 account_index、api_key_index 与 private_key，或使用 API 凭据一表中列出的环境变量。Nautilus 的 account_id 与场所账户索引 是两回事：使用上表中的 issuer，例如 LIGHTER-001 或 LIGHTER_ROBINHOOD-001。

  6. 确认目标部署能识别所选的账户与 key 索引：

    LIGHTER_SETUP_ACCOUNT_INDEX="123456"
    LIGHTER_SETUP_API_KEY_INDEX="4"

    curl -sS --get \
      "${LIGHTER_SETUP_API_URL}/api/v1/apikeys" \
      --data-urlencode "account_index=${LIGHTER_SETUP_ACCOUNT_INDEX}" \
      --data-urlencode "api_key_index=${LIGHTER_SETUP_API_KEY_INDEX}"

    成功会返回 "code": 200 与所选的 key。这次公共查询只确认索引，既不暴露也不校验私钥。

注意

Lighter API key 授权交易、私有账户访问以及部分 withdrawal 操作。把私钥存放在 secret manager 或受保护的环境配置中，不要提交到仓库，也不要出现在日志里。

集成方归因​

通过 Lighter 合作伙伴计划，执行客户端 会把 Lighter Mainnet 上的创建与修改交易在 L2TxAttributes 中归因到 NautilusTrader 的集成方 账户。这适用于所有层级（包括 Standard）以及列表中的每一笔订单。maker 与 taker 的集成方费用 为零。

在 Lighter Mainnet 上，启动时会对非 maker-only 的 key 用 L2 签名提交 ApproveIntegrator， 全部最大费用设为零，不需要 L1 签名。

Lighter Testnet 与两个 Robinhood 环境把 L2TxAttributes 留空，并在启动时省略 ApproveIntegrator。

选择 Robinhood Mainnet 即让账户加入 NAUTILUS 推荐码。启动时，客户端用配置的 L2 API key 把该推荐码应用到账户的公共 L1 地址。失败只记 warning，不阻塞交易。Robinhood Testnet 不做 推荐归因。

归因跟随类型化的部署与环境，与自定义场所名无关。

maker-only 的 Lighter Mainnet key 无法提交 ApproveIntegrator，会跳过自动批准。这类 key 要 通过适配器交易，同一账户上必须先由一个非 maker-only 的 key 批准该集成方：批准作用于账户 范围。

吊销批准​

离开该适配器时要吊销 Lighter Mainnet 的批准，用 approval_expiry = 0 与零最大费用发送 ApproveIntegrator。下次用非 maker-only key 启动执行客户端时，会在所有 Lighter Mainnet 层级 重新续期零费用批准。

export LIGHTER_API_KEY_INDEX=5
export LIGHTER_API_SECRET=REPLACE_ME
export LIGHTER_ACCOUNT_INDEX=123456
cargo run -p nautilus-lighter --bin lighter-integrator-revoke           # Lighter Mainnet

脚本源码： crates/adapters/lighter/bin/integrator_revoke.rs。

# Python (PyO3 binding) - reads the same env vars as the Rust bin
from nautilus_trader.adapters.lighter import revoke_lighter_integrator

订单簿数据​

簿增量与深度订阅在订阅前会拒绝 BookType::L2_MBP 之外的类型。

只有 subscribed/order_book 会初始化 WebSocket 簿。在它到达之前，适配器丢弃 update/order_book 帧且不发出簿数据，因为增量消息不含未变化的档位。

深度与增量共用 WebSocket 的 order_book 流。每个被接受的快照或增量更新都会刷新一份前 10 档 深度视图。

K 线​

K 线订阅使用 candle/{market_id}/{resolution}。Lighter 大约每 500 毫秒批量推送未收盘 K 线的 更新。适配器只在 candle 起始时间戳前进时，为每个已收盘周期发出一个 Bar。重连与退订会 清空进行中的缓存。

REST 与 WebSocket 支持 1m、5m、15m、30m、1h、4h、12h 与 1d。适配器对 REST 请求接受 1w，但 Lighter Mainnet 会以 20001 invalid param 拒绝该分辨率， REST 模式也未列出它。周 K 线订阅会在本地返回 错误。要得到周数据，请聚合更短的 K 线。

REST 历史会跳过 OHLC 缺失、为 null 或非正的缺口行：它们无法构成有效的 Nautilus K 线。之后 有效的行仍会加载。

金融工具状态与成交​

金融工具状态订阅会重放缓存的 orderBookDetails 状态，或拉取一份 REST 快照。Lighter 没有 WebSocket 的状态变更流。

成交订阅使用公共 WebSocket 流。历史使用公共 /api/v1/recentTrades，无需凭据。适配器把最多 100 笔成交过滤到请求的时间区间内，不分页。

实时与历史资金费率的语义见资金费率。

不支持的数据请求​

request_quotes 未实现：适配器用到的 REST 端点没有带时间戳的报价快照或历史，无法安全映射到 QuoteTick。要获取实时最优买卖价，请订阅 WebSocket 的 ticker 流。

request_book_depth 未实现：REST 簿端点没有可用于 OrderBookDepth.ts_event 的场所事件时间戳。 实时深度请用 subscribe_book_depth，REST 的 OrderBook 快照用 request_book_snapshot。

订单簿恢复​

序列校验​

适配器把每条增量更新的 begin_nonce 与上一份簿的 nonce 比对。不匹配时抑制簿输出，并启动 一次退订/订阅替换。

场所的 offset 不是连续性计数器：它可能跳号，重连后也可能因服务器不同而变化。参见 Lighter 订单簿契约。

快照要求​

订阅写操作完成后，初始订阅与替换订阅最多等待 book_snapshot_timeout_secs（默认 10 秒）以 取得类型化的 subscribed/order_book 快照。设为 0 可禁用快照期限。

快照缺失会启动或重试恢复，即使已收到控制确认或 Already Subscribed 响应。控制确认只释放 订阅槽位，不算完成簿恢复。

只有在匹配的快照替换掉缓存档位之后，簿输出才恢复。空快照同样会清空簿。

重试限制与重连​

每个恢复事件在 180 秒内最多做八次替换尝试，采用指数退避与抖动；之后在 [1 分钟, 15 分钟] 区间 内按指数退避继续重试，直到快照被接受。替换用的退订与订阅写操作指向同一连接。

重连会淘汰过期的订阅代次，同时保留恢复事件及其剩余预算。预算耗尽、正处在尝试间隔中等待的 恢复，会在新连接上立即重试。

消费者与持续失败​

同一市场的增量与深度共用一个恢复事件：

  • 移除一个消费者时，另一个保持不变。
  • 移除最后一个消费者会取消待处理的写操作与快照等待。
  • 关闭会取消其持有的全部工作。

恢复不会以失败状态结束。被拒绝的替换，或重连后回放的订阅，会按递增的间隔继续重试。迟到的 快照仍能恢复簿。

除限流以外的场所订阅失败，会让正在等待的初始 subscribe 调用失败，即使恢复已经启动。此后 恢复只在还有其他消费者时继续。后续的 subscribe 会重新开始，其他市场各自独立恢复。

共享的恢复机制与适配器职责见 订单簿恢复的归属。

实时恢复验证​

用 lighter-book-stress 在六个 Lighter 主网永续簿上验证同步与恢复的改动。它不提交订单，会 检查簿流契约（包括每个快照事件内 nonce 递增），并与馈送最优 20 档的独立重建结果比对。

在仓库根目录运行：

CARGO_BUILD_JOBS=16 bash scripts/strip-adapter-env.bash \
  cargo test -p nautilus-lighter --features examples --test lighter-book-stress -- --timeout 10 --rounds 12

--scenario 选择运行方式：

  • churn（默认）：先验证无重连的恢复，再轮换 nonce 缺口、丢弃与延迟快照、被拒的替换、重连， 以及恢复期间的重启。
  • initial：在全新会话中每轮丢弃每个簿的首个快照。
  • boundaries：让重试预算内的每次尝试都被拒，然后检查重试上限、结束上限等待的重连、恢复期间 的退订，以及重连期间的关闭。

--timeout 设置快照超时秒数（0 禁用期限）；--rounds 设置轮数（默认 12）。

该工具需要主网 WebSocket 流以及公共 orderBooks 与 orderBookDetails API。共享参数与输出 格式见压力测试工具。

订单能力​

订单标识​

Lighter 使用数字场所订单索引与调用方提供的 client_order_index。适配器从 Nautilus ClientOrderId 派生一个 31 位索引，冲突时向后探测。

探测出的值在重启后无法重新推导。转换订单与成交报告之前，对账会通过核心缓存解析每个场所订单 ID，并恢复其真实的 client 索引：缓存中的活动订单回到活动跟踪，终态订单使用有界回放跟踪。

恢复绝不单凭整数推断 client order ID。对账必须包含该订单，且核心缓存必须保留其场所订单 ID 映射；否则报告用唯一的场所订单 ID 作为其外部 client order ID。

查询对活动与终态历史都使用数字场所订单 ID。在该 ID 已知之前，派生的 client 索引只能查询活动 订单。活动匹配出现重复时按歧义失败。

组合要求​

  • 所有腿使用同一个永续金融工具、策略与订单列表 ID，client order ID 各不相同。
  • OTO 父单使用 MARKET 或 LIMIT。其子单方向与父单相反，使用 reduce_only，且请求数量与 父单相同。
  • OCO 兄弟使用 reduce_only，共享同一方向与数量。这一对包含一个止损（STOP_MARKET 或 STOP_LIMIT）与一个止盈（MARKET_IF_TOUCHED 或 LIMIT_IF_TOUCHED）。

  • 子单共享一个非零有效期。
  • 市价与 IOC 限价父单使用零有效期。

要做原生括号单，请选择 OCO 退出腿与条件止盈。适配器会拒绝默认的 OrderFactory.bracket——它使用 OUO 退出腿与普通 LIMIT 止盈。适配器不会用撤销代替数量 更新，也不会把挂着的限价单转换成触发的止盈。

子单激活与规模​

Lighter 根据父单的执行来激活 OTO/OTOCO 子单并确定其规模。在此之前，其 wire 基础数量为零。 由 Nautilus 提交、处于挂起状态的子单的报告保留请求数量，场所侧数量变化会产生 OrderUpdated。

场所数量为零的挂起子单不能被修改。适配器既不提供了结放量控制，也不提供独立的按比例缩放。

撤销行为​

Lighter 的 OCO 在止损/止盈订单触发时就撤销兄弟订单，即使尚未成交；而 Nautilus 的 OCO 在 成交或撤销时才请求对端撤销。适配器保留场所的触发即撤销行为，不重建兄弟订单。事件顺序可能 延迟撤销的送达。见 原生子单成交与持仓对账。

对活动的 Nautilus OCO 腿调用 cancel_order，会同时请求撤销其活动对端，使用两个独立交易： Lighter 的单订单撤销会让对端留在场上，且两者各自可能成功或失败。

要等目标腿的 OrderAccepted。其对端需要已知的场所绑定或保留的组合提交索引。 batch_cancel_orders 同样会带上活动的 OCO 对端，每个选中的订单只提交一次。

注意

原生组合请保持 StrategyConfig.manage_contingent_orders = false（默认值）。开启本地或有管理 可能在场所之外独立改变子单规模，或在场所撤销其 OCO 对端时撤掉一个已触发但未成交的退出单。

触发事件与关系恢复​

条件订单使用 标记价触发。 条件限价单发出 OrderTriggered；市价类条件单没有中间的 TRIGGERED 状态直接成交，遵循 Nautilus 语义。

只要有本地订单上下文或缓存的场所绑定，即使 Lighter 在激活后清掉了父单链接，报告仍保留 Nautilus 的 client、parent 与 linked ID。全新启动的客户端在处理第一条私有流的订单或成交之前， 会先恢复缓存的所有权关系。

已触发的条件限价单保留其 Nautilus 类型与最后已知的触发价。无法恢复触发价的外部订单会报告为 活动中的 LIMIT 订单。

触发之后，改价与改量会发送零触发价；再次改变触发价不受支持。独立的事务批次不会获得或有关系。

GTD 策略​

在默认的 use_gtd = true 下，策略的 expire_time 成为场所的 GoodTillTime 有效期。适配器 接受 [5 分钟 + 1 秒, 30 天] 的生命周期，额外的一秒用于容纳签名与传输。

wire 层的有效期仍是 GoodTillTime：Lighter 没有 GoodTillCancel，所以 use_gtd = false 不能 像在 Binance 那样切换它。

本地管理跳过原生的 5 分钟下限，但会拒绝超过 28 天的策略到期时刻——那种情况下场所会先过期。 更长的生命周期请用原生 GTD。场所的撤单延迟仍会推迟订单移除。

订单列表与批量操作​

非或有的 SubmitOrderList、BatchModifyOrders 与 BatchCancelOrders 使用 WebSocket 的 jsonapi/sendtxbatch，保留每个子单的签名交易与订单事件归属。它们既不提供原子执行，也不提供 或有关系。

本地校验会拒绝无效的提交子单，或拒绝无效的修改子单，同时让受支持的兄弟订单继续。每批最多 15 个交易：31 个受支持的子单通常拆成 15、15、1 三批。并发的 nonce 分配或恢复可能产生更小的 批次。

每个批次使用独立的限流令牌与确认。拒绝只影响其自身的子单。

签名下一批之前，适配器最多等待 10 秒以收取当前批的确认。超时后继续派发，并保留未确认的 条目供对账。

CancelAllOrders 走同一批处理路径，保留任何方向过滤。场所的 活动与挂起订单上限仍然适用：将一条命令拆分并不会增加账户 在某个市场上可持有的订单数。

或有列表必须恰好包含一个受支持的原生组合，由两或三条永续订单组成，共用一个 CreateGroupedOrders 交易与 nonce。任何一条腿无效都会让整组被拒。

Lighter 的交易指南给出的上限是 50，而其 WebSocket 参考写的是 15。 适配器采用较低的那个文档值。

Nonce 分配与交易准入​

每个批次使用同一个账户与 API key，在 Lighter 的 nonce 契约下取连续 nonce。 skip_nonce=0 时，适配器必须保持 nonce 顺序。

本地窗口允许每个 key 有 16 个未确认的分配，不是乱序的场所交易。未签名的子单会等待容量或 nonce 恢复，不会被丢弃。关闭会停止派发并丢弃队列中剩余的工作。

批量响应按请求 ID 与签名交易哈希关联。

确认只表示交易被准入，不表示订单被接受、修改或撤销。失败取决于拒绝发生的时点：

  • 准入前的拒绝会让整批失败且不消耗 nonce。无效 nonce 的响应还会刷新 nonce 基线。
  • 准入后，单个交易可能失败而其他成功。应用阶段的失败会消耗 nonce；应用前被排序者拒绝可能 使该 nonce 未被消耗，从而让该 key 上后续的 nonce 失效。

参见 nonce 消耗。

投递结果不明确时，适配器保留待处理状态供对账，不重发该批。

修改确认​

每个订单最多只能有一个未决的修改。要等它的 OrderUpdated 或 OrderModifyRejected 之后再改 一次。第二次请求会直接收到 OrderModifyRejected，且不会裁决第一次。

待处理的撤销会拒绝修改。待处理的修改期间，撤销仍可用，但其结果要等修改裁决之后。

确认需要一次交易查找，并与当前场所订单形态匹配。受影响的 WebSocket 订单帧与成交会一直等待， 直到适配器发出 OrderUpdated 或 OrderModifyRejected。可能应用该修改或成交的 HTTP 报告， 要等缓存应用该事件之后才处理。

请求修改待处理期间的行为
单订单状态查找可能把未变化的活动报告作为 PendingUpdate 返回。
批量订单报告与 mass status暂扣该订单，并把结果标记为不完整。
query_order不发出报告。

这可能带来几秒的报告延迟。持仓对账会暂扣受影响的金融工具，直到其执行事件进入缓存。

原生子单成交与持仓对账​

对原生 OTO/OTOCO 子单，真实成交要等到终态场所订单与完整的真实成交覆盖确立有效数量之后才发出。 适配器先发布该数量，再发布成交，随后对账终态状态。

挂起的子单在其修改裁决之后才发布触发事件。

未决的子单成交或修改也会暂扣同一策略与金融工具后续的成交与终态事件。成交按场所事件时间顺序 放行，到达顺序用于打破并列。可能应用这些改动的 HTTP 报告要等缓存追上。

在子单关闭且真实成交覆盖完整之前，缓存的成交与持仓核算可能滞后。

这段延迟期间：

  • 包含受影响金融工具的范围，其持仓查询会失败。
  • mass status 会省略受影响持仓的报告与合成的平仓报告，并保持不完整。
  • 场所持仓快照在私有流上仍然可用。

结果恢复​

订单更新与交易查找用于裁决创建与撤销子单。恢复在待处理动作仍是当前动作期间，最多做三次查找， 间隔两秒，并校验交易哈希、类型、账户、API key 与原始提交 nonce。

已准入的修改（单批或批量）确定失败时，发出一个 OrderModifyRejected，并清除其匹配的待处理 动作，不回滚已消耗的 nonce。

延迟的结果不能清除较新的修改，也不能拒绝一个已被恢复确认的修改。

注意

若有界查找无法确认某次修改，它可能在本次会话剩余时间内保持未决，从而暂扣后续订单事件与 成交，并拒绝再次修改。适配器既不假设成功，也不重发。要再次管理该订单，请先重启并对账 场所状态。

修改探测在重连之间保留其原始提交身份。撤销探测在连接变化时停止。

撤销恢复也包括 PendingCancel 之外的订单，例如 CancelAllOrders 的目标。缓存中的订单只有在 分派时处于 PendingCancel 才会收到 OrderCancelRejected，否则只记录失败日志。

杠杆更新与签名校验​

报告完整性​

每次有界的 mass status 对失活订单与成交使用同一个截止时刻。完整性的要求是：所有必需的订单、 成交与持仓来源都成功，且每条历史成交都能映射到其订单。

被暂扣的事件、未决的修改，或尚未应用到缓存的更新，都会让被暂扣的订单、成交与持仓来源变成 不完整。

仅历史失败不会否决可用的活动订单或显式的持仓报告。范围内没有持仓报告的有界历史成交，遵循 引擎的 仅订单投影规则。

trades 参考不保证历史深度，因此回看窗口可能 超出可用的成交。分页从最新的成交往回走。只有找到早于回看起点的成交才能证明覆盖完整：

  • 有早于起点的成交：报告集保持完整。
  • 先耗尽游标：适配器记录未覆盖的区间，并把报告集标记为不完整。
  • 没有保留任何成交：不可能有内容被截断，报告集保持完整。

游标耗尽无法区分"被截断"和"确实没有更早的成交"：新账户可能在什么都没缺的情况下报告不完整。 请选一个场所能够供出数据的回看窗口。

更早的成交可以通过场所的 历史数据导出获取，最多 12 个月的账户成交。 适配器不读取 export 端点。

启动时的持仓检查​

若 account_all_positions 比其对应成交的处理早几毫秒到达，在策略启动时开仓可能出现瞬时的 cached=0, venue=N warning。应用该成交后差异自行消解，不会生成对账订单。

账户与持仓管理​

已认证的执行客户端订阅这些私有流：

  • account_all_orders：订单状态报告。
  • account_all_trades：成交报告。
  • account_all_positions：初始持仓快照与实时更新。
  • account_all_assets：按资产的余额快照（现货余额加永续抵押物）。
  • user_stats：永续账户的保证金汇总（抵押物与可用余额）。

适配器只在 account_all_assets 与 user_stats 的首帧都到达之后，才发出二者的合并状态。

构造允许凭据缺失；connect() 要求已解析的 private_key、account_index 与 api_key_index。私有账户流与 nonce 刷新是必需的。

持仓快照与更新​

永续在每个市场使用一个净额持仓，现货余额使用账户资产状态。权威的 subscribed/account_all_positions 快照会：

  • 把未出现的市场和 position 为零的行拍平为平仓。positions 映射为空会拍平整个缓存。
  • 对未映射或无法解析的行保留缓存持仓，避免出现假的平仓报告。

有界对账会跟踪快照的市场覆盖范围，重连使其失效。被触碰过但缺失的市场，只有在当前快照覆盖下 才产生显式的平仓报告。未映射或畸形的行会让 mass status 保持不完整，而不是证明已平仓。

增量的 update/account_all_positions 帧替换非零持仓、把显式的零行拍平，并保留未出现的持仓。 空更新保留全部持仓。

限流​

Lighter 同时限制 IP 与 L1 地址。数据与执行客户端各有独立的 REST 限流器，默认按 Standard 配额。 请把两者合计的流量规划在场所限制之内。

更高的层级需要显式的本地配额：

  • rest_quota_per_min：两个客户端上的读请求每分钟；未设置默认 60。
  • sendtx_quota_per_min：仅执行客户端上的交易请求每分钟；未设置时独立于 rest_quota_per_min 默认 60，位于独立的桶。

这些选项只改变本地限速。公共数据仍不需认证，更高的本地配额不会让它享受账户级的场所限制。

请求桶与端点权重​

场所对每个 L1 地址在 HTTP 与 WebSocket 之间共享一个交易桶。一次 WebSocket sendTxBatch 计为 一次，最多携带 15 个适配器交易。

Standard 账户的读与交易共享 60 请求/分钟。Plus 与 Premium 使用分开的场所桶。适配器在所有 层级都分开本地的读取与交易限流器，因此 Standard 用户必须把合计流量（包括 nonce 与对账的读取） 一起规划。

REST 限流器每次调用消耗一个令牌，忽略场所权重。请按你的端点组合设置 rest_quota_per_min。 Lighter Mainnet 的 Premium 限额是 24,000 加权请求/分钟，在不计入其他请求时，下面两种速率任一 都可承受：

  • 40 次 /api/v1/recentTrades/分钟（权重 600）。
  • 120 次 /api/v1/trades/分钟（权重 200）。

请确认你所在部署的权重。

交易类型限制​

Lighter 的默认交易类型限制是 40 请求/分钟，带有按类型的例外，与层级的 sendTx/sendTxBatch 限制相互独立。

Lighter 主网测试中，每次报价漂移都改价的报价策略，在一分钟内约 40 次修改后会撞到 code=23000（Too Many Requests）。修改还要消耗 交易量配额。

交易密集的报价请把 sendtx_quota_per_min 设为 40 或更低。这个共享限流器同时也为创建与撤销 限速。批次最多 15 个交易只消耗一个令牌，因此该设置不会限制订单列表或批量修改中的子单数量。 批量子单的交易类型限制请按你的部署确认。

本地配额允许突发，不是严格的滚动分钟上限。配额 30 会允许最初 30 次请求的突发，并按 30/分钟 补充，可能超过场所 60 秒 40 次的限制。请为突发和共享同一 L1 地址的其他客户端留出余量。

要是有界地测试 Standard，每分钟 15 次交易请求与 5 次 REST 调用可以给独立的账户检查留出空间。

无法关联的 WebSocket 23000 响应只记日志，不会判定某一笔交易失败。它可能来自非交易流量， 因此适配器不猜测是哪个订单或批次失败。未决的结果要靠对账解决，不要盲目重发。

共享的适配器限流器​

一个执行限流器在 WebSocket 的 sendTx 与 sendTxBatch（提交、修改与撤销），以及启动集成方 批准所用的 HTTP sendTx 上统一执行 sendtx_quota_per_min。原始调用在配置了该值时使用它， 否则回退到原始客户端的 REST 限流器。

WebSocket URL 字符串完全相同的客户端共享一个 200 消息/分钟的限流器，用于非交易的控制帧。 默认数据 URL 的 readonly=true 使其拥有与执行分离的限流器。请把合计的控制流量规划在场所的 按 IP 限制之内。

每条连接的订阅闸门允许 35 个未确认请求，这个数目取决于确认延迟而非发送速率。它不执行场所 跨连接的每 IP 50 条消息上限。sendTx 与 sendTxBatch 既不消耗客户端消息桶，也不消耗场所的 inflight 上限。

连接管理​

心跳与重连​

WebSocket 客户端每 30 秒发送一次心跳，并按 [250 毫秒, 30 秒] 的指数退避重连。90 秒内没有入站 帧就重连，即使场所还留着那个已停滞的 socket。Pong 会在没有行情的情况下刷新这个窗口。

私有认证​

私有认证令牌的有效期最长 8 小时。适配器签发 7 小时的令牌，每 6 小时轮换并重新订阅。透明的 重连会签发新令牌，并在被跟踪的订阅开始回放之后重新订阅账户流。

Nonce 恢复​

执行端重连时通过 GET /api/v1/nextNonce 刷新 nonce 基线。在刷新或其后台重试为新连接装好基线 之前，单笔提交、修改与撤销命令无法签名。批量命令（包括刷新期间收到的）会等待就绪。

同一会话内：

  • 场所确认会推进本地 nonce 窗口。
  • 确定性拒绝或移交前的失败可能回滚其最新 nonce。
  • 过期的状态会触发一次 GET /api/v1/nextNonce 重同步。

可能已到达场所的结果会保留其待处理 nonce 与订单身份，交给 WebSocket 或对账恢复。

账户流就绪​

LighterExecutionClient::connect() 会清空旧的持仓与账户缓存，然后最多等待 30 秒，让全部五条 私有流就绪。

只有 subscribed/account_all_positions 能满足持仓就绪，实时更新不算；REST 账户负载永远不会作为 回退。

透明的重连与认证轮换不会重新进入 connect()。它们保留持仓，直到下一次 subscribed/account_all_positions 套用快照替换规则。实时更新以合并方式应用，不逐出未出现的 市场。

签名需要三项凭据：

  • 账户索引：Lighter 账户的数字标识。

  • API 私钥：40 字节的十六进制私钥，可带或不带 0x 前缀。

配置示例​

use nautilus_lighter::{
    common::enums::{LighterDeployment, LighterEnvironment},
    config::{LighterDataClientConfig, LighterExecutionClientConfig},
};
use nautilus_model::identifiers::AccountId;

let data_config = LighterDataClientConfig::builder()
    .environment(LighterEnvironment::Testnet)
    .deployment(LighterDeployment::Lighter)
    .build();

let exec_config = LighterExecutionClientConfig::builder()
    .environment(LighterEnvironment::Testnet)
    .deployment(LighterDeployment::Lighter)
    .account_id(AccountId::from("LIGHTER-001"))
    .build();

let robinhood_data_config = LighterDataClientConfig::builder()
    .environment(LighterEnvironment::Mainnet)
    .deployment(LighterDeployment::Robinhood)
    .build();

let robinhood_exec_config = LighterExecutionClientConfig::builder()
    .environment(LighterEnvironment::Mainnet)
    .deployment(LighterDeployment::Robinhood)
    .account_id(AccountId::from("LIGHTER_ROBINHOOD-001"))
    .build();

这些执行配置使用其部署与环境对应的 凭据环境变量；显式的凭据字段会覆盖它们。

设置 LiveExecutionEngineConfig.reconciliation_instrument_ids 可限定对账范围，设置 reconciliation_lookback_mins 可为失活订单与成交的重放设定边界。
