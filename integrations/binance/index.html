Binance

Binance 创立于 2017 年，按日交易量和加密资产及衍生品未平仓合约计，是全球最大的加密货币交易所之一。

NautilusTrader 提供 Binance 集成，用于实时行情数据与实时交易。适配器（adapter）以 Rust 实现，并通过相同的 公开配置、工厂和数据类型暴露给 Python。

支持的产品：

  • Binance Spot（含 Binance US）
  • Binance USDT-Margined Futures（加密货币与 TradFi 永续；当期与次期的周、月、季交割合约）
  • Binance Coin-Margined Futures（永续与当期或次季交割合约）

概览​

适配器暴露以下公开组件：

  • BinanceDataClientConfig 与 BinanceExecutionClientConfig：实时客户端配置。
  • BinanceInstrumentProviderConfig：金融工具选择、过滤与警告策略。
  • BinanceDataClientFactory 与 BinanceExecutionClientFactory：交易节点客户端工厂。
  • load_binance_instruments：独立的配置化金融工具发现。
  • load_binance_order_book_deltas：Rust 实现的 Binance 深度 CSV 加载器，用于订单簿数据整理。
  • BINANCE、BINANCE_CLIENT_ID、BINANCE_VENUE 及 client order ID 解码器：公开标识符与解码工具。
备注

多数用户只需要配置与工厂，按实时节点配置所示装配到实时交易节点即可。 其余组件服务于独立加载与离线解码。

底层 HTTP 与 WebSocket 客户端、它们的缓存，以及产品专有的 instrument provider 对象都不通过 Python API 暴露。请使用实时配置与工厂，或独立的金融工具加载器，不要依赖这些内部实现。

独立发现金融工具时，传入与实时客户端相同的数据客户端配置和 provider 配置：

import asyncio

from nautilus_trader.adapters.binance import BinanceDataClientConfig
from nautilus_trader.adapters.binance import BinanceInstrumentProviderConfig
from nautilus_trader.adapters.binance import BinanceProductType
from nautilus_trader.adapters.binance import load_binance_instruments

config = BinanceDataClientConfig(
    product_type=BinanceProductType.USD_M,
    instrument_provider=BinanceInstrumentProviderConfig(
        load_all=False,
        load_ids=["BTCUSDT-PERP.BINANCE"],
    ),
)
instruments = asyncio.run(load_binance_instruments(config))

该函数支持 Spot、USD-M 与 COIN-M，使用配置中的环境、URL、代理、接收窗口、Binance US 模式、 过滤器、警告策略和手续费率策略。Margin 不是 Binance 支持的产品，会被拒绝。

处理 Binance 深度 CSV 数据时，直接调用无状态加载器：

from nautilus_trader.adapters.binance import load_binance_order_book_deltas

df = load_binance_order_book_deltas(path, nrows=1_000_000)

加载器保留源数据值与列顺序。文件打开失败、数值或方向值非法都会抛出 RuntimeError。

信息

每个 Binance 客户端实例只处理一种产品类型。配置使用单数的 product_type 字段，实时工厂从一份 配置创建一个数据或执行客户端。若要在同一节点同时运行 Spot 与 Futures，需配置不同 ID 的独立客户端， 例如 BINANCE_SPOT 与 BINANCE_FUTURES。策略订阅或提交订单时，传入匹配的 client_id。 同时使用两个执行客户端时，按执行客户端路由 配置显式的 BINANCE 场所路由或默认客户端。完整的客户端搭建方式见当前的 Python 示例。

数据类型​

该集成包含若干自定义数据类型：

  • BinanceSpotTicker：Spot 24 小时行情数据，含价格、成交量与成交统计。
  • BinanceFuturesTicker：Futures 24 小时行情数据，含价格与统计信息。
  • BinanceBar：带附加成交量指标的 bar 数据，适用于历史与实时场景。
  • BinanceFuturesMarkPriceUpdate：Futures 标记价格数据，含预估结算价。
  • BinanceFuturesLiquidation：来自 forceOrder 流的 Futures 强平事件。
  • BinanceFuturesOpenInterest：当前 Futures 未平仓合约快照（仅限请求）。
  • BinanceFuturesOpenInterestHist：某周期内的 Futures 未平仓合约历史（仅限请求）。

完整定义见 Binance API Reference。

BinanceBar、BinanceFuturesTicker、BinanceFuturesOpenInterest 和 BinanceFuturesLiquidation 支持在 data/custom/{TypeName}/{identifier} 路径下做 Arrow/Parquet 数据目录持久化。Rust 构建需启用 nautilus-binance 的 arrow feature 标志才能持久化。仍使用旧式 Python 写入布局 data/custom_<snake_case> （例如 data/custom_binance_bar）的数据目录，可用 nautilus catalog migrate-parquet 迁移。

符号体系​

现货与期货合约尽可能使用 Binance 原生符号。NautilusTrader 支持多场所交易，必须区分 现货交易对 BTCUSDT 与永续期货合约 BTCUSDT（Binance 对两者使用同一符号）。

Nautilus 在 USD-M 永续符号后追加 -PERP。例如 Binance USD-M 的 BTCUSDT 永续变为 BTCUSDT-PERP。USD-M 的 TRADIFI_PERPETUAL 上架合约使用相同后缀，XAUUSDT 变为 XAUUSDT-PERP。

适配器将 TRADIFI_PERPETUAL 上架合约映射为 PerpetualContract，并从 Binance 的 underlyingType 推导其资产类别：

Binance underlyingTypeNautilus 资产类别
EQUITY、CN_EQUITY、KR_EQUITY、HK_EQUITY、PREMARKETEquity
COMMODITYCommodity

取值为其他值或缺失的上架合约会被跳过，并输出警告。

COIN-M 永续保留 Binance 原生的 _PERP 后缀，因此 BTCUSD_PERP 保持不变。

交割符号保留 Binance 的 _YYMMDD 后缀。例如 BTCUSDT_270326 与 BTCUSD_270326 在 Nautilus 内原样保留。USD-M 支持文档中的 CURRENT_MONTH、NEXT_MONTH、 CURRENT_QUARTER、NEXT_QUARTER 合约类型，另加 Binance 通用定义未列出的周度类型 CURRENT_WEEK 与 NEXT_WEEK。COIN-M 支持 CURRENT_QUARTER 与 NEXT_QUARTER。 合约可用性随环境和上架周期变化。

USD-M 交割金融工具为线性，以保证金资产结算。COIN-M 交割金融工具为反向，以保证金资产（基础货币） 结算，并使用 Binance 的 contractSize 作为金融工具乘数。两者都用 onboardDate 和 deliveryDate 表示激活与到期。参见 Binance 官方的 USD-M 通用定义 和 COIN-M 通用定义。

Rust Futures 数据测试器无需修改源码即可接受交割金融工具：

BINANCE_FUTURES_INSTRUMENT_ID=BTCUSDT_270326.BINANCE \
  cargo run -p nautilus-binance --example binance-futures-data-tester --features examples

现货名义价值限制​

通过 SBE 或 JSON 加载的现货金融工具，会从 MIN_NOTIONAL 与 NOTIONAL 过滤器填充专用的 min_notional 和 max_notional 字段。两个过滤器同时存在时，解析器采用最严格的边界。 这些字段以对应货币的精度保存计价货币的 Money 值。

风险引擎结合自身价格估计检查这些金融工具字段。金融工具的 info 是给下游 actor 和策略的 元数据，不影响风险决策。Binance 在交易所侧验证订单时会应用它自己的市价单标志与参考价规则。

PostgreSQL 在恢复金融工具时会保留金融工具元数据。升级现有数据库后，在仓库根目录运行 nautilus database init --schema "$PWD/schema/sql" 以添加元数据存储。此前被丢弃的元数据 需要重新加载金融工具定义才能恢复。

GTD 策略​

Binance Spot 的有效期取值 只有 GTC、IOC 与 FOK。Spot 没有原生 GTD 或 goodTillDate。

USD-M 对 LIMIT 以及 STOP 和 TAKE_PROFIT 的限价形式支持原生 GTD。适配器将普通订单 经 HTTP 或 WebSocket 交易通道发出，独立批次经 HTTP batchOrders，条件 algo 订单经 HTTP algoOrder。Binance 的 WebSocket algo schema 包含 goodTillDate，但其 timeInForce 枚举 不含 GTD，因此适配器不通过该端点路由 GTD algo 订单。

COIN-M 文档中的订单 API 没有原生 GTD 值或 goodTillDate 参数。参见官方 USD-M 交易 API 和 COIN-M 通用定义。

USD-M 的 goodTillDate 是毫秒级 epoch 时间戳，Binance 会忽略其中的亚秒部分。若过期时间不在 整秒边界上，Nautilus 直接拒绝，而非静默取整。过期时间必须严格大于当前时间加 600 秒，且严格 小于 253402300799000。原生 GTD 还会拒绝市价单、post-only 订单，以及任何没有过期时间的订单。

use_gtd=True 是默认值：使用原生 USD-M GTD，并在 Spot 和 COIN-M 上拒绝原生 GTD。仅当提交订单 的策略设置了 manage_gtd_expiry=True 时才将 use_gtd 设为 False。此时适配器发出警告并 发送 GTC，由 Nautilus 在本地过期时刻撤单。

撤销全部订单的行为​

默认情况下，Strategy.cancel_all_orders() 对该策略关联的订单逐笔发送撤销。使用 strategy_only=False 时，策略向适配器发送一条范围更大的 CancelAllOrders 命令。适配器 会同时纳入 open 和 inflight（SUBMITTED）状态的订单，因此也会撤销 Binance 尚未确认的订单。

多策略安全：多个策略交易同一金融工具时，适配器将发起策略关联的订单与该金融工具的全部 订单比对。若全部订单都属于该策略，则使用一次 cancel-all API 调用；否则按策略分别发送撤销 （普通订单用批量，algo 订单逐笔），避免影响其他策略。

方向过滤：带 order_side 的 CancelAllOrders 命令只撤销该金融工具指定方向的挂单。 Spot 对每笔匹配的订单各发一笔撤销；Futures 将普通订单批量处理、algo 订单逐笔撤销。带方向的 请求只在挂单中筛选，因此 Binance 尚未确认的 inflight（SUBMITTED）订单不会被它撤掉。 要覆盖这类订单，需使用不带方向的 cancel-all。

Futures algo 订单：条件订单类型（STOP_MARKET、STOP_LIMIT、TAKE_PROFIT、 TAKE_PROFIT_MARKET、TRAILING_STOP_MARKET）需要使用不同的撤销端点。适配器会自动路由到 正确端点。algo 订单触发并转为普通订单后，改用标准撤销端点。

提交、修改与撤销的重试策略​

执行客户端对每条提交、修改、撤销命令只发送一次。首次请求可能已到达撮合引擎，因此超时、网络 故障或 Binance 返回未知状态时不会盲目重试。重试可能产生重复订单或重复施加第二次修改。

  • 本地提交校验失败在发送前发出 OrderDenied。本地修改校验失败发出 OrderModifyRejected。 交易所的明确拒绝发出对应的拒绝事件。
  • 传输结果不明确时订单保持 inflight 状态，由私有流或 REST 对账确定结果。交易所结果未知期间， 适配器不会发出虚假的拒绝事件。
  • Futures algo 撤单可能从触发前的 algo 端点回退到普通订单端点。这是订单触发后的端点切换， 不会向同一端点重复发送同一条撤单。
  • 命令结果不明确期间，策略代码不得重新提交。等待对账，或按 client order ID 查询订单。

BinanceDataClientConfig 和 BinanceExecutionClientConfig 为 HTTP GET 请求暴露 max_retries、retry_delay_initial_ms 和 retry_delay_max_ms。瞬时读取失败按有界指数退避 重试，并刷新认证字段。交易所的 Retry-After 头决定最小延迟，可能超过 retry_delay_max_ms。 重试总预算固定为 180 秒。当所需等待超过剩余预算时，请求直接返回交易所错误，不再等待。

这些设置不会重试订单命令，因为重发结果不明确的命令可能重复下单或重复修改。

Binance Futures 会针对风险事件生成交易所订单：

  • 强平：保证金不足以维持持仓时，Binance 按破产价强制平仓。这些订单的 client ID 以 autoclose- 开头。
  • ADL（自动减仓）：保险基金耗尽时，Binance 平掉盈利持仓以覆盖亏损。这些订单的 client ID 前缀为 adl_autoclose。

  • 交割（COIN-M）：到期的交割合约自动平仓，client ID 以 delivery_autoclose- 开头。
  • 保险基金：保险基金承接时使用 NEW_INSURANCE 状态（公开 changelog 已弃用，但线上流量 中仍可见）。

  1. 记录带订单详情的 warning 日志，便于监控。
  2. 生成含正确成交明细、流动性方向为 TAKER 的 FillReport。
  3. 生成用于对账的 OrderStatusReport。

手续费估算​

Binance 的成交事件省略手续费字段（N/n）时，适配器按计价货币以 default_taker_fee * qty * price 估算手续费。这只适用于 USD-M 线性合约。COIN-M 反向合约 以零手续费作为回退，因为线性公式未考虑合约大小。在 BinanceExecutionClientConfig 上配置 default_taker_fee 以匹配你的费率档位（默认：0.0004 / 0.04%）。

Futures 成交历史保留期​

Binance 保留 USD-M 与 COIN-M 最近三个月的账户成交记录，但未说明这是自然月还是固定时长， 因此适配器以最近 88 天作为完整的 Futures 成交历史窗口。

generate_fill_reports 拒绝早于该窗口的显式起点。边界取命令的 ts_init，并限制其最多落后 当前客户端时间 12 小时。指定结束时间时必须同时提供开始时间。

对 mass status，reconciliation_lookback_mins 未设置或超过完整窗口时，按完整窗口处理。 返回的 ExecutionMassStatus 将 lookback_start 设为实际采用的边界，reports_complete 设为 false。参见mass-status 历史契约。 Binance Spot 不受影响。参见 Binance Futures 变更日志。

事件序列​

订单带 price_match 提交时：

  1. Nautilus 带 priceMatch 参数发送订单，API 请求中省略限价价格。
  2. Binance 接受订单并确定实际挂单价格。
  3. Nautilus 发出 OrderAccepted 事件。
  4. 若 Binance 接受的价格与参考价不同，Nautilus 发出 OrderUpdated 事件，携带实际挂单价格。
  5. Nautilus 缓存中的订单价格与 Binance 接受的价格保持一致。

示例​

order = strategy.order_factory.limit(
    instrument_id=InstrumentId.from_str("BTCUSDT-PERP.BINANCE"),
    order_side=OrderSide.BUY,
    quantity=Quantity.from_int(1),
    price=Price.from_str("65000"),  # Reference price for local risk checks
)

strategy.submit_order(
    order,
    params={"price_match": "QUEUE"},
)
备注

若 Binance 以不同价格接受订单（例如 64,995.50），你会先收到 OrderAccepted 事件，随后收到 带新价格的 OrderUpdated 事件。

RPI​

Binance RPI（Retail Price Improvement，零售价格改进）使用 timeInForce=RPI。它是 post-only 的，只与来自 Binance App 或 Web 的合资格零售订单撮合。

Nautilus 通过 Binance 专有的 rpi 参数暴露该能力。只能用于 post_only=true 的 USD-M LIMIT 订单，且只支持单笔 SubmitOrder 命令，SubmitOrderList 会被拒绝。不带 rpi 的普通 post-only 订单仍使用 GTX。交易所侧细节见 Binance 的 USD-M Futures API 定义。

RPI 仅对 GET /fapi/v1/exchangeInfo 响应中 permissionSets 包含 RPI 的 symbol 可用。 提交 RPI 订单前先确认 symbol 资格。参见 Binance 的 RPI 指南。

Rust 示例假定 order 是合资格 symbol 的 post-only LIMIT 订单。Python 侧需把 instrument_id 设为合资格金融工具，并按其交易规则选择 quantity（Quantity）与 price（Price）。

use nautilus_core::params::Params;

let mut params = Params::new();
params.insert("rpi".to_string(), true.into());
self.submit_order(order, None, None, Some(params))?;
order = strategy.order_factory.limit(
    instrument_id=instrument_id,
    order_side=OrderSide.BUY,
    quantity=quantity,
    price=price,
    post_only=True,
)

strategy.submit_order(order, params={"rpi": True})

平仓​

Binance Futures 的条件订单支持 closePosition，触发时平掉整个持仓。触发时 Binance 在服务端 按当前持仓大小确定数量。参见官方 USD-M Algo Service API 和 COIN-M Algo Service API。

与 reduce_only 不同，closePosition 会跟随持仓大小变化；持仓以其他方式关闭时，Binance 会 自动撤销该订单。

在 Nautilus 的 StopMarket 或 MarketIfTouched 订单上设置 reduce_only=true，再在其 params 中传入 close_position=true。reduce-only 标志记录订单的平仓意图，交易状态为 REDUCING 时它是订单通过校验的必要条件。适配器把这一组合翻译为 Binance 的全平指令，并 拒绝在订单列表中使用 close_position。

在风险引擎配置中允许 Binance 的整仓退出：

from nautilus_trader.adapters.binance import BINANCE_VENUE
from nautilus_trader.config import LiveRiskEngineConfig

risk_engine = LiveRiskEngineConfig(
    full_position_exit_venues=[BINANCE_VENUE],
)

允许列表默认为空。没有该条目时，占位数量会像普通订单一样接受最小数量、最大数量和名义价值 检查。提交订单时传入持仓 ID，风险引擎才能验证这次退出是在减少该持仓。

let params = Params::from([("close_position", true.into())]);
self.submit_order(order, Some(position.id), None, Some(params))?;
strategy.submit_order(
    order,
    position_id=position.id,
    params={"close_position": True},
)
信息

Nautilus 订单必须设置 reduce_only=true，但 Binance 不允许 closePosition=true 与其 reduceOnly 字段同时使用。因此适配器发送 closePosition=true，同时在 Binance 请求中 省略 quantity 和 reduceOnly。对冲模式下还会发送平仓方向的 positionSide。

对已列入允许列表的场所，风险引擎仍会校验数量精度与正数、触发价、订单形态与方向，以及关联的 持仓。它不会把最小/最大数量和名义价值边界应用到占位数量上。

注意

只有当场所配置的执行客户端强制执行整仓平仓语义时才添加该场所。不解析 close_position 的执行 客户端可能只按标准 reduce-only 路径提交占位数量，而不是平掉整个持仓。

移动止损​

在 Binance 上使用移动止损市价单时：

  • 用 activation_price（可选）指定移动机制的激活时刻。
  • 省略时，Binance 以提交时的当前市场价为准。
  • 回撤比率用 trailing_offset，配 TrailingOffsetType.BASIS_POINTS。适配器拒绝其他偏移 类型，也拒绝超出 Binance 0.1% 至 10% 范围的回撤比率。
注意

移动止损订单不要用 trigger_price：会直接报错。改用 activation_price。

Link & Trade​

适配器为支持的 client order ID 加上 NautilusTrader 集成 ID 前缀，以适配 Binance 的 Link and Trade 计划。无需用户做任何配置。

适配器会压缩外发的 ClientOrderId 以适配 Binance 的 36 字符上限，并在事件到达策略前解码 入站事件。支持的格式包括数字工厂 ID、UUID，以及带短字母数字交易者/策略标签的连字符工厂 ID， 例如 O-20260922-160119-V2-000-8。

短标签格式中，一个标签支持一到两个 ASCII 字母或数字，另一个标签必须是 [0, 1023] 内的数字 值并至少补零到三位。计数支持 [0, 4194303] 且不含前导零，时间戳范围为 UTC [2020-01-01 00:00:00, 2156-02-07 06:28:15]。use_uuid_client_order_ids 可选项。

不超过 24 字节的自定义 ID 无需压缩。更长且不支持的 ID，适配器记录 warning 并原样发送不带 前缀的 ID。Binance 的长度与字符限制仍然适用。

升级后的存量订单​

现有的数字、UUID 和原始前缀编码保持不变。解码器同时接受历史的无前缀 ID。对带短标签 ID 但 没有交易所订单 ID 的存量订单操作，适配器会同时查询其编码形式与历史无前缀形式。若两者分别 指向不同订单，该操作会被判为歧义并拒绝。

修改与撤单使用找回的交易所订单 ID。Spot 的撤销-替换（cancel-replace）在替换同一逻辑订单时 保留原有网络上的 client order ID，包括以历史无前缀 ID 提交的订单。即使变更通过 WebSocket 传输，这些查找同样生效。

解码 client order ID​

直接查询 Binance（REST API、网页 UI 或自写 HTTP 代码）时，clientOrderId 字段是编码后的 形式。两个工具函数可还原出原始的 Nautilus ClientOrderId：

from nautilus_trader.adapters.binance import (
    decode_binance_futures_client_order_id,
    decode_binance_spot_client_order_id,

# Encoded ID from a Binance REST response or the web UI
encoded = "x-TD67BGP9-T0000000000000"
original = decode_binance_spot_client_order_id(encoded)
# Returns "O-20200101-000000-000-000-0"

# Futures equivalent
encoded_futures = "x-aHRE4BCj-T0000000000000"
original_futures = decode_binance_futures_client_order_id(encoded_futures)

不带 broker 前缀的字符串原样返回，因此对任意 clientOrderId 值调用都是安全的。

备注

凡返回 OrderStatusReport 这类 Nautilus 类型的地方，适配器都会自动解码。只有在适配器 之外工作时才需要手动解码：直接 REST 查询、Binance 网页 UI 或原始交易所报文。

快照请求​

显式订单簿快照请求独立于订阅同步：

  • Spot：深度范围 [1, 5000]。
  • Futures：深度为 5、10、20、50、100、500 或 1000。

快照同步与恢复​

Futures 增量深度订阅，以及未指定显式深度的 Spot L2_MBP 订阅，会保持增量深度流处于订阅状态， 并通过共享簿恢复机制用 REST 快照为簿播种。

同步​

同步在订阅或数据 WebSocket 重连后的第一条增量处启动：

  1. 缓冲增量并请求 REST 快照。
  2. 丢弃被快照 lastUpdateId 覆盖的缓冲增量。
  3. 剩余增量必须紧接快照之后，否则重新请求快照。
  4. 先把快照发送到 DataEngine，再发送剩余的缓冲增量。
  5. 之后每条增量发送前先与上一条校验衔接。

每条增量必须紧接快照或上一条增量：

产品快照后的第一条增量后续增量
SpotU <= lastUpdateId + 1U <= previous u + 1
FuturesU <= lastUpdateId <= upu == previous u

违反这些规则的增量即为序列缺口：停止输出簿数据，缓冲增量，并在不重新订阅的情况下请求新快照。 解析失败的增量会在下一条增量处表现为缺口。

恢复限制​

  • 快照超时：book_snapshot_timeout_secs（默认 10 秒）限定每次快照请求的期限。设为 0 则交由 HTTP 客户端超时控制。
  • 重试预算：每次恢复在 180 秒内最多尝试 8 次快照，采用指数退避加抖动。预算耗尽后按 从 1 分钟翻倍至 15 分钟的间隔继续重试。请求永久失败则直接进入该间隔。
  • 重连：重连后从新流重新同步，仍在进行的恢复保留其剩余预算。预算耗尽后处于等待间隔的 恢复会立即重试一次。该恢复的下一次快照可以在新流交付增量之前为簿播种，此时第一条增量必须 紧接该快照。
  • 持续失败：恢复持续进行，直到某个快照能衔接缓冲的增量，或该簿被退订。其他簿各自独立继续。

快照限速​

快照请求消耗每个客户端在场所属请求权重预算中的份额。重连后的一波重新同步会等待预算，而不是 超出预算：

产品快照预算突发（预算的一半）单次全量快照开销
Spot3,000 / 分钟1,500250（5000 档）
Futures1,200 / 分钟60020（1000 档）
  • 首个快照的排队不消耗恢复的重试次数和 180 秒预算。
  • 显式快照请求消耗同一预算。
  • HTTP 客户端对失败快照请求的重试不受限速控制。

盘口时间戳​

QuoteTick 的 ts_event 字段随传输方式不同。Spot SBE 使用微秒级事件时间戳。Spot 公共 JSON 的 bookTicker 消息可能缺少事件时间戳，此时适配器使用 ts_init。Futures 使用成交时间。

K 线与历史行情数据​

Spot 支持秒级 kline 的订阅与历史请求。实时 Spot kline 订阅要求 spot_market_data_mode=Json，因为 Binance 不在 Spot SBE 上发布 kline 或 ticker 流。Binance Futures 拒绝秒级 kline，因为 Futures API 不提供。

已收市的场所 kline 会发出一个核心 Bar 和一个 BinanceBar 自定义数据事件。BinanceBar 保留 计价成交量、成交笔数、主动买入基础成交量与主动买入计价成交量。历史核心 bar 请求返回 Bar。 需要历史响应保留扩展字段时，用 bar_type 元数据请求 BinanceBar 自定义数据。

实时成交订阅在 Futures 上使用 <symbol>@aggTrade 流，因为 Binance 的 Futures WebSocket 只发布 聚合成交；在 Spot 上使用逐笔的 <symbol>@trade 流。

无边界的历史成交请求使用 recent-trades 端点。带时间边界的请求使用聚合成交，最多接受 1000 条， 因此数据源跟随请求而非配置项。Spot 把给定边界直接传给 /api/v3/aggTrades。Futures 接受任一端 边界落在最近 24 小时内；同时给出两端时，区间必须短于一小时。

历史核心 bar 请求接受外部聚合的时间 bar，并使用对应的场所 kline 端点。内部聚合的 bar 由 DataEngine 基于原始成交、盘口或源 bar 响应，通过 bar_types 请求参数构建，Binance 数据 客户端不做聚合。

资金费率​

适配器通过 subscribe_funding_rates 将 FundingRateUpdate 作为一等数据类型发出。数据来自 Mark Price Stream WebSocket 端点，它随标记价格与指数价格一并提供当前资金费率和下次结算时间。三个订阅 （subscribe_mark_prices、subscribe_index_prices、subscribe_funding_rates）通过引用计数 共用一条 @markPrice@1s 流。

历史资金费率通过 request_funding_rates 获取，它查询 Get Funding Rate History REST 端点（USD-M 为 GET /fapi/v1/fundingRate，COIN-M 为 GET /dapi/v1/fundingRate）。 每行历史记录映射为一个 FundingRateUpdate，ts_event 设为资金费结算时间。历史记录行的 next_funding_ns 字段为 None，因为端点不提供该值。

适配器还通过 BinanceFuturesMarkPriceUpdate 自定义数据订阅暴露场所报文 （见 Binance 专有数据）。

对 Binance 而言，FundingRateUpdate.interval 为 None。Mark Price Stream 与资金费率历史 端点都不包含资金费率周期字段。Binance 通过 Get Funding Rate Info REST 端点暴露 fundingIntervalHours，但适配器不消费它。

金融工具状态轮询​

数据客户端定期轮询 Binance exchangeInfo，检测金融工具交易状态的变化。当某个 symbol 在不同 状态间切换（例如从 Trading 到 Halt，或临近到期的期货合约从 Trading 进入 Delivering），适配器 发出 InstrumentStatus 事件。

轮询间隔默认 3,600 秒（60 分钟），可在数据客户端配置中用 instrument_status_poll_secs 调整。 设为 0 可完全禁用轮询。

初次连接时，适配器用 exchange info 响应为状态缓存播种，不发事件。之后的轮询检测到状态变化 才发出 InstrumentStatus 事件。若某 symbol 从 exchange info 中消失（例如退市或合约到期后）， 适配器发出 NotAvailableForTrading。

状态轮询不会重新加载金融工具定义。独立的 instrument_refresh_interval_secs 任务执行完整的 带过滤目录加载：原子替换数据客户端与 WebSocket 查找表，然后把刷新后的金融工具发给数据引擎 并更新状态快照，同时刷新执行客户端的精度缓存。

完整刷新间隔默认 3,600 秒，设为 0 禁用。断开连接会取消该任务，重连时用新的取消令牌启动 一个替换任务。

适配器限速​

适配器在场所计量之前运行自己的令牌桶限流器。每个 HTTP 请求从按产品划分的请求桶取一个令牌， 每个订单操作额外从订单计数桶取一个令牌：

产品请求订单操作
Spot1,200/分钟10/秒，100,000/天
Futures（USD-M 与 COIN-M）2,400/分钟300/10 秒，1,200/分钟

订单计数桶覆盖该产品支持的全部订单操作，不只是下单：提交、OCO 提交、批量提交、algo 提交、 修改（Spot 的修改经撤销-替换实现）、批量修改、撤单、全撤、批量撤单、algo 撤单。撤单 频繁和改单频繁的策略同样受这些桶约束。非订单类认证请求，例如调整杠杆与保证金类型、维持 listen-key 的 keepalive，只消耗请求桶。

请求桶按调用次数计数而非权重，与场所的权重计量并不一致。连续调用高权重或动态权重端点 （权重 20 的 /api/v3/allOrders，或随 limit 增长的 /klines）时，场所权重的消耗快于本地 桶的记账。大规模历史请求可能需要人工控制节奏。实际场所用量可通过响应头 X-MBX-USED-WEIGHT-* 监控。订单簿快照请求还会等待权重感知的预算，见快照限速。

Futures Credits Trading Mode（BNFCR）​

Binance Futures Credits Trading Mode 是面向欧盟监管的模式。USD-M 期货钱包、保证金、盈亏与费用 全部以 BNFCR 计价。这种内部记账单位替代稳定币余额，与美元 1:1 锚定。

BNFCR 不是可交易资产，因此适配器将其映射到执行配置中的 bnfcr_currency（默认 USDT）， 使账户余额与佣金按所交易合约的结算稳定币对账。交易 USDC 本位永续时将 bnfcr_currency 设为 USDC。其他无法识别的期货资产会注册为通用加密货币，而不是报错。

密钥类型​

适配器使用 Ed25519 或 HMAC-SHA256 签名，并根据 API secret 的格式自动识别密钥类型， 无需配置。能解析为 PKCS#8 Ed25519 私钥的 secret 用 Ed25519 签名，其余一律按 HMAC secret 处理。

强烈推荐使用 Ed25519。 Binance 推荐 Ed25519，因其性能与安全性更好。未来版本的 NautilusTrader 将只支持 Ed25519。

提示

现在就切换到 Ed25519 密钥。生成 Ed25519 密钥对并注册到 Binance，见下文 生成 Ed25519 密钥。

备注

Ed25519 密钥必须以未加密的 PEM 格式提供（base64 编码的 ASN.1/DER）。实现会自动从 DER 结构 中提取 32 字节种子。不支持加密（带密码）的 PEM 密钥。若密钥已加密，先解密： openssl pkey -in encrypted.pem -out decrypted.pem

生成 Ed25519 密钥​

方式 1：OpenSSL（推荐）

# Generate private key (PKCS#8 PEM format)
openssl genpkey -algorithm ed25519 -out binance_ed25519_private.pem

# Extract public key
openssl pkey -in binance_ed25519_private.pem -pubout -out binance_ed25519_public.pem

方式 2：Binance 密钥生成器

从发布页下载 Binance Asymmetric Key Generator 并运行它生成密钥对。

注册到 Binance

  1. 登录 Binance，进入 Profile -> API Management。
  2. 点击 Create API，选择 Self-generated。
  3. 粘贴公钥文件的全部内容，包括 -----BEGIN PUBLIC KEY----- 头尾行。
  4. 配置权限（Enable Spot & Margin Trading 等）。

在 NautilusTrader 中使用

把私钥设为 API secret：

export BINANCE_API_KEY="your-api-key-from-binance"
export BINANCE_API_SECRET="$(cat binance_ed25519_private.pem)"

或直接在配置中传入 PEM 内容。

注意

妥善保管私钥。绝不外传，也不要提交到版本库。

凭据可以直接传给配置对象，也可以设置对应的环境变量（各环境的变量见 环境）。

提示

所有客户端都使用 Ed25519 密钥。HMAC 密钥目前对数据客户端和执行客户端仍然可用，但 Ed25519 性能更好，且将在未来版本成为唯一支持的密钥类型。见密钥类型。

注意

Spot 的 BINANCE_ED25519_* 和 BINANCE_*_ED25519_* 环境变量已被移除。发现这类变量的客户端 会记录 error 并按凭据缺失处理。Futures 侧它们已被弃用，带警告暂时生效，未来版本会移除。 请改名为 BINANCE_API_KEY / BINANCE_API_SECRET（Ed25519 密钥现在会自动识别）。

交易节点启动时，你会收到凭据是否有效、是否具备交易权限的确认信息。

产品类型​

配置通过 product_type 字段与 BinanceProductType 枚举选择一种受支持的产品：

  • SPOT
  • USD_M（USDT、USDC 或 BNFCR 抵押品）
  • COIN_M（加密货币抵押品）
备注

保证金交易尚未实现。其他枚举值会被实时客户端与独立金融工具加载器拒绝。见 产品支持。

Base URL 覆盖​

可覆盖 HTTP REST 与 WebSocket API 的默认 base URL。配置 API 集群，或使用 Binance 专门提供的 定制端点时，这很有用。

Binance US​

在配置上设置 us=True 可获得一等公民的 Binance US Spot 路由。Binance US 不是自定义 URL 的 别名。该开关选择以下端点与传输方式：

  • api.binance.us。
  • 公共 JSON 流。
  • HMAC 签名的 HTTP 执行。
  • 443 端口带周期性 keepalive 的 listen-key 私有流。

该路由背后的场所约定见 Binance US 官方 REST API、 行情流 和用户数据流 文档。

支持的组合是有意为之的：

  • 数据：product_type=Spot、environment=Live、spot_market_data_mode=Json。
  • 执行：product_type=Spot、environment=Live。下单使用 HTTP，私有事件走 listen-key 流。
  • Futures、Testnet、Demo，以及带 us=True 的 Spot SBE 配置都无法通过校验。

Binance US 的公共 JSON 覆盖实时行情、深度快照、近期与聚合成交历史、kline 历史，使用账户级 maker/taker 费率。Global Binance 在 us=False 且 spot_market_data_mode=Json 时保持现有的 免凭据 Spot JSON 行为。

金融工具加载​

instrument provider 控制选择与过滤：

from nautilus_trader.adapters.binance import BinanceInstrumentProviderConfig

instrument_provider = BinanceInstrumentProviderConfig(
    load_all=False,
    load_ids=["BTCUSDT.BINANCE", "ETHUSDT.BINANCE"],
    filters={"quotes": ["USDT"], "bases": ["BTC", "ETH"]},
    log_warnings=True,
    query_commission_rates=True,
)

load_all=False 时只选择 load_ids，场所过滤器再按交集生效。支持的过滤器有 symbols、 bases、quotes，Futures 另有 contract_types。取值为字符串或非空字符串列表，匹配不区分 大小写。适配器拒绝 filter_callable，请使用支持的声明式过滤器。

解析出的金融工具不携带 maker 或 taker 费率。query_commission_rates 不会把账户佣金复制到 金融工具上。

解析警告​

某些 Binance 金融工具的字段值超出平台处理能力，无法解析为 Nautilus 对象。这些金融工具会被 跳过并发出警告。

批量加载期间，非交易状态的 symbol 以 debug 日志跳过。若通过 load_ids 或 symbols 过滤器 显式选中，它们仍会发出警告。

要抑制这些警告：

from nautilus_trader.adapters.binance import BinanceInstrumentProviderConfig

instrument_provider = BinanceInstrumentProviderConfig(
    load_all=True,
    log_warnings=False,
)

Futures 对冲模式​

Binance Futures 对冲模式允许同一金融工具同时持有多空两个方向的持仓。

use_position_ids 开启时（默认），Futures 订单与成交报告包含由金融工具和 Binance 持仓方向 推导的 venue_position_id。对冲模式的 REST 持仓报告使用同样的 ID，例如 ETHUSDT-PERP.BINANCE-LONG。该标识在 REST 历史、用户流更新、流恢复、交易所生成成交以及 跟踪的 TRADE_LITE 成交中全程保持。

One-way 模式的 BOTH 持仓、订单与成交保持无键，使用净额对账。只有为 OmsType.HEDGING 的虚拟持仓（持仓标识由引擎管理）才把 use_position_ids 设为 false。use_position_ids=True 时，若提交的自定义持仓 ID 与 Binance 对冲腿的规范 ID 不同，适配器会在发送订单前拒绝。

使用对冲模式需先在 Binance 侧开启，然后在 BinanceExecutionClientConfig 上设置 oms_type=OmsType.HEDGING，并保持 use_position_ids=True 以跟踪场所的两侧持仓：

from nautilus_trader.adapters.binance import BinanceExecutionClientConfig
from nautilus_trader.adapters.binance import BinanceProductType
from nautilus_trader.model import AccountId
from nautilus_trader.model import OmsType

config = BinanceExecutionClientConfig(
    account_id=AccountId.from_str("BINANCE-001"),
    product_type=BinanceProductType.USD_M,
    oms_type=OmsType.HEDGING,
    use_position_ids=True,
)

启动对账要分别保留 LONG 与 SHORT 腿，必须使用这一配置。

若缓存中某笔开仓的 Binance 对冲持仓带有不同的本地生成 ID，适配器会拒绝该持仓行，并同时 报告缓存 ID 与期望 ID。请先修正缓存状态，再重试启动。适配器不会为旧 ID 做别名，也不会 创建重复的场所持仓。

COIN-M / USD-M 架构​

Binance COIN-M Futures（CM / DAPI）与 USD-M Futures（UM / FAPI）共享统一架构。本节说明 这对适配器的影响。

完整细节见 Important CM-UM Integration Notice。

WebSocket 流​

行情流的负载在 <symbol>@aggTrade、<symbol>@ticker、<symbol>@bookTicker、 <symbol>@depth<levels>、<symbol>@miniTicker 及所有 !*@arr 流上都带有 st（symbol 类型：1 = UM，2 = CM）。UM 侧的单 symbol 流在 <symbol>@bookTicker、 <symbol>@depth<levels>、<symbol>@miniTicker 和 <symbol>@rpiDepth 上还带 ps （pair symbol）。

适配器用 serde 解码 JSON，默认忽略未知字段，因此这些字段被静默丢弃。

全市场数组流（!ticker@arr、!miniTicker@arr、!bookTicker、!forceOrder@arr、 !contractInfo）在 fstream 和 dstream 上传递 UM + CM 合并后的内容。

REST 与 WebSocket API​

  • 下单与改单的确认响应不包含 avgPrice / cumQuote / cumBase。适配器从用户数据流获取 成交。查询端点（GET /{f,d}api/v1/order、userTrades）仍返回这些字段。
  • PUT /dapi/v1/order（COIN-M 改单）要求同时提供 price 和 quantity。适配器总是两个 字段都发，修改命令省略的那个回退为缓存订单的值。
  • COIN-M 条件订单（STOP、TAKE_PROFIT 等）使用 /dapi/v1/algoOrder 端点。适配器将所有 futures 条件订单路由到 algo order API。
  • GET /dapi/v1/openOrders 传入非法 symbol 时返回错误 -1121。

限流池​

UM 与 CM 共享 Binance 的限流池：每 IP 2400 权重/分钟，每账户 1200 订单/分钟和 300 订单/10 秒。 同一进程内环境或自定义端点作用域相同、出口路径相同的 Rust futures HTTP 客户端，在 UM 与 CM 之间共享请求权重状态；认证使用同一 API key 时，无论出口路径如何，UM 与 CM 共享订单计数状态。

Live、testnet、demo 及无关联的自定义端点作用域保持隔离。不同的配置出口路径有各自独立的 请求权重状态，不同的 API key 有各自独立的订单计数状态。不同进程，以及同一 Binance 账户使用 多个 API key 的情形，仍需外部协调。

dualSidePosition​

UM 与 CM 共享同一个 dualSidePosition 设置，任何一侧的修改都会同时影响两侧。翻转该设置前， 确保 UM 和 CM 都没有挂单和持仓。
