OKX

OKX 创立于 2017 年，是一家提供现货、保证金、永续互换、期货、期权、价差与事件合约交易的加密货币 交易所。本集成支持在 OKX 上接入实时行情数据与订单执行。

概览​

该适配器（adapter）以 Rust 实现，通过 PyO3 绑定暴露给 Python，不依赖外部 OKX 客户端库。

OKX 适配器包含多个组件，可单独或组合使用：

  • OKXHttpClient：底层 HTTP API 连接。
  • OKXWebSocketClient：面向 Rust 调用方的底层 WebSocket API 连接。
  • OKXDataClient：行情数据订阅管理器。
  • OKXExecutionClient：账户管理与交易执行网关。
  • OKXDataClientFactory：OKX 数据客户端工厂。
  • OKXExecutionClientFactory：OKX 执行客户端工厂。
备注

多数用户按下面的方式配置实时交易节点即可，无需直接使用这些底层组件。

金融工具更新​

数据客户端在连接时通过 REST 加载金融工具缓存，并为每个配置的金融工具类型订阅 OKX 的 instruments WebSocket 频道。所有更新路径都遵循配置的金融工具类型、family 与合约类型，未变化的定义不会重复发布。

来源触发向下游发布
连接加载连接时的 REST完整缓存，一次
Instruments 频道场所推送（增量）新增或变化的定义，每条附带 InstrumentStatus
REST 对账update_instruments_interval_mins（默认 60）仅新增或变化的定义

每次更新先写入数据客户端、HTTP 与 WebSocket 缓存，然后把新增或变化的定义作为 DataEvent::Instrument 发布，因此消费者不会观察到缓存中缺失的定义。除 ts_event 与 ts_init 之外的任何序列化字段变化都算实质变化。

  • Instruments 频道是增量流而非快照流。订阅或重连可能没有初始负载，因此仅靠重连回放无法让金融工具 缓存保持一致。
  • 把间隔设为 0 可禁用周期性对账。Instruments 频道更新始终会应用。每条连接生命周期内运行一个刷新 任务，在断开、连接失败清理、停止与释放时取消。设置 load_spreads 时会一并包含价差金融工具。
  • 从 REST 响应中消失的金融工具保留在缓存中，它们可能仍支撑着打开的订阅。停牌、到期与退市通过 instruments 频道以 InstrumentStatus 事件到达。

订单簿订阅​

Rust 与 Python v2 对 L2 market-by-price（L2_MBP）订单簿支持以下订阅：

订阅交付方式深度
subscribe_book_deltas场所更新时发出 OrderBookDeltas。每侧 50 或 400 档；价差为五档。
subscribe_book_depth原生 OrderBookDepth 快照。每侧最多五档。
subscribe_book_at_interval按间隔发出缓存的 OrderBook。保留所选频道的全部档位。

subscribe_book_depth 使用 OKX 原生 books5 快照，变化时按 100 ms 节奏发布。depth=None 默认五档。[1, 5] 内的请求从每个快照中选取最优的若干档。更大的请求和 rpi=True 会被拒绝。 价格、数量与场所订单数直接取自每个快照，适配器不用增量数据重建深度快照。

增量与间隔订阅沿用现有的频道选择逻辑：[1, 50] 内的请求在配置的 VIP 等级允许时选 50 档频道， 否则选公共 400 档 books 频道；其他深度选 400 档频道。rpi 参数为 true 时选 books-rpi。 频道访问仍受 OKX 账户权限约束。

在同一客户端内，原生深度消费者按金融工具共用一个请求上限，包括非托管订阅。请求深度冲突会被拒绝。

原生深度使用与增量和间隔簿相互独立的馈送。退订其中一路，另一路保持活动。价差金融工具沿用现有的 共享五档 sprd-books5 快照馈送，在增量与深度消费者都退订之前保持活动。

托管簿只有一个更新来源：增量或深度。兼容的托管订阅共享该来源，但同一金融工具的托管深度不能与 托管增量或间隔订阅共存。数据引擎在改动托管簿之前拒绝冲突请求。同一来源的各消费者必须在客户端、 簿类型、深度与订阅参数上保持一致。只有当该来源的全部消费者都是非托管时，不同客户端才能使用 不同配置。

要同时接收增量与深度，在增量订阅上设 managed=True，在深度订阅上设 managed=False。非托管 深度回调随后不会改动由增量托管的簿。两者同时启用时 DataTester 采用这一安排。

间隔交付使用数据引擎现有的增量订阅与定时器。它发布全部保留的档位，不受非托管深度消费者请求上限 的影响。连接中断或簿恢复期间，定时器可以继续发布最后缓存的簿。原生深度交付在重连后以新的完整 快照恢复，不依赖增量恢复。恢复限制见订单簿恢复。

订单簿恢复​

数据客户端对每个增量簿独立恢复。恢复期间抑制增量更新，并替换订阅以请求新快照。只有客户端接受 快照后输出才恢复，而这要求替换用的退订与订阅请求已经发出。被接受的快照替换全部现有价位。 空快照清空订单簿。

恢复触发条件​

以下情形启动恢复：

  • 出现序列缺口。
  • 初始订阅发送失败。
  • 初始或重连后的快照超时。
  • 场所拒绝簿订阅。

出现序列缺口时，客户端丢弃不匹配的批次并抑制后续增量更新。book_snapshot_timeout_secs 设定 快照期限。初始订阅的期限从订阅发出后开始计时，不含等待发送的时间。

重连会重置受影响套接字上的簿同步。价差簿在业务套接字上接收完整快照，其恢复只由初始发送失败、 初始或重连后快照缺失、订阅被拒触发。

陈旧馈送检查只记录 warning，并跳过正在运行的恢复所持有的簿。它不会启动恢复，因为清淡市场 合法地可能长时间没有簿变化。

重试循环与限制​

适配器使用共享簿恢复机制。 每个金融工具一个恢复循环，直到新快照被接受，或退订与关闭将其取消。恢复不会以失败状态结束。

订阅请求发出后，簿保持恢复状态，直到新快照被接受。

  • 尝试次数：初始预算内最多八次。
  • 初始预算：180 秒，包含发送、等待快照与重试延迟。
  • 延迟：第一次重试立即执行。之后按一秒起步的指数退避，抖动最多一秒，上限十秒。
  • 预算耗尽后：按从 1 分钟翻倍到 15 分钟的间隔继续尝试，抖动最多五秒。每次尝试受一分钟约束， 快照超时更长时受快照超时约束。不可重试的拒绝直接进入该间隔。

进行中的恢复跨重连沿用现有预算，避免在替换的退订与订阅请求之间被取消。预算耗尽后处于尝试间隔 等待的恢复，会在新连接上立即重试。替换订阅会保留其重连意图。退订与关闭会取消恢复。

持续失败​

重试预算耗尽后，客户端记录一条 error，此后每次失败尝试记一条 warning。按十五分钟的间隔， 持续失败的簿每小时约发八次订阅请求。场所已不再服务的金融工具可能出现这种情况。该速率远低于 OKX 每条连接每小时 480 次的上限。迟到快照在任何时刻都能完成恢复。要停止恢复就退订。

快照关联限制​

增量簿频道只在建立或恢复同步期间接受快照。同步完成后，客户端丢弃主动发来的快照，不替换簿也不 重置其序列号。周期性发布完整快照的频道则持续接受。

簿订阅发送会等待目标连接上传输写操作完成。替换操作中的两次发送使用同一连接。连接发生变化时 该次尝试判为失败。

快照接受不会把订阅确认与恢复尝试做关联。较早订阅产生的延迟快照可能在替换发出时仍在队列中， 并在闸门打开时完成当前恢复。写确认并不能消除这种歧义。当场所响应只标识簿频道与金融工具时， 恢复也无法可靠区分退订错误与订阅错误。

禁用快照期限​

book_snapshot_timeout_secs 设为 0 会禁用快照期限，包括初始与重连后检查。序列缺口和订阅 拒绝仍会启动恢复。

重试预算内，快照缺失会让当前尝试一直等待，直到以下事件之一发生：

  • 客户端接受了一个快照。
  • 收到拒绝。
  • 恢复被取消。
  • 180 秒初始预算结束。

预算之后的尝试仍按上文所述的边界受控。

实时恢复验证​

okx-book-stress 压力测试工具用于验证簿同步与恢复的改动。它连接 OKX 主网公共行情，不提交任何 订单。它按簿流契约校验输出的现货、RPI 互换与价差簿，并与场所馈送最优 20 档的独立重建结果比对。

该工具在无重连的情况下验证恢复，包括启用期限时丢弃替换快照。随后注入序列缺口、丢弃和延迟快照、 强制重连，并在恢复期间执行退订与关闭。

在仓库根目录运行：

CARGO_BUILD_JOBS=16 bash scripts/strip-adapter-env.bash \
  cargo test -p nautilus-okx --features examples --test okx-book-stress -- --timeout 10 --rounds 18

--scenario 选择运行方式：

  • churn（默认）：上文描述的故障轮。
  • initial：在全新会话中每轮丢弃每个簿的首个快照。
  • turnover：在恢复期间退订并重新订阅簿。
  • boundaries：探测替换截断、重试耗尽进入重试上限，以及重连期间关闭。

--timeout 设置快照超时秒数，0 表示禁用快照期限；--rounds 设置轮数（默认 18）。

该工具需要访问公共与业务 WebSocket 端点，以及公共金融工具和价差 API。簿生命周期的自动化测试使用 本地 mock 服务器。共享参数与输出格式见压力测试工具。

符号体系​

OKX 为不同金融工具类型使用特定的符号约定。在 Nautilus 中引用金融工具时加上 .OKX 后缀， 例如 BTC-USDT.OKX。

各金融工具类型的符号格式​

SPOT​

格式：{BaseCurrency}-{QuoteCurrency}

示例：

  • BTC-USDT - 比特币对 USDT（Tether）
  • BTC-USDC - 比特币对 USDC
  • ETH-USDT - 以太坊对 USDT
  • SOL-USDT - Solana 对 USDT

在策略中订阅现货比特币 USD：

InstrumentId.from_str("BTC-USDT.OKX")  # For USDT-quoted spot
InstrumentId.from_str("BTC-USDC.OKX")  # For USDC-quoted spot

SWAP（永续互换）​

格式：{BaseCurrency}-{QuoteCurrency}-SWAP

示例：

  • BTC-USDT-SWAP - 比特币永续互换（线性，USDT 本位）
  • BTC-USD-SWAP - 比特币永续互换（反向，币本位）
  • ETH-USDT-SWAP - 以太坊永续互换（线性）
  • ETH-USD-SWAP - 以太坊永续互换（反向）

线性与反向合约：

  • 线性（USDT 本位）：用 USDT 等稳定币作保证金。
  • 反向（币本位）：用基础加密货币作保证金。

FUTURES（到期期货）​

格式：{BaseCurrency}-{QuoteCurrency}-{YYMMDD}

示例：

  • BTC-USD-261225 - 2026 年 12 月 25 日到期的比特币期货
  • ETH-USD-261225 - 2026 年 12 月 25 日到期的以太坊期货
  • BTC-USD-270326 - 2027 年 3 月 26 日到期的比特币期货

期货可以是线性或反向。适配器依据 OKX 的 ctType 字段推导。

SPREADS（价差）​

格式：{Leg1InstrumentId}_{Leg2InstrumentId}

示例：

  • BTC-USDT_BTC-USDT-SWAP - BTC-USDT 现货与 BTC-USDT 永续互换之间的价差
  • ETH-USD-SWAP_ETH-USD-261225 - ETH-USD 永续互换与到期期货之间的价差

在数据客户端上设置 load_spreads=True，即可从 OKX 的 Get Spreads (Public) 端点加载实时 OKX 价差金融工具。适配器把每个 OKX sprdId 映射为带 .OKX 场所后缀的 Nautilus 价差金融工具 ID。

价差金融工具说明：

  • 价差行情流经 OKX 业务 WebSocket：盘口（sprd-bbo-tbt）、成交（sprd-public-trades）与 五档簿快照（sprd-books5）。价差没有增量簿频道。每条 sprd-books5 更新以 OrderBookDepth 发给深度订阅者，以带快照标志的 OrderBookDeltas 发给增量订阅者。
  • 解析器支持现货、互换、期货腿的组合，也支持 OKX 通过同一价差端点返回的含期权腿的价差定义。
  • OKX 的期权 RFQ 与大宗交易流程独立于 Nitro 价差订单簿 API，不走这条价差路径。

OPTIONS（期权）​

格式：{BaseCurrency}-{QuoteCurrency}-{YYMMDD}-{Strike}-{Type}

示例：

  • BTC-USD-261225-100000-C - 比特币看涨期权，行权价 $100,000，2026 年 12 月 25 日到期
  • BTC-USD-261225-100000-P - 比特币看跌期权，行权价 $100,000，2026 年 12 月 25 日到期
  • ETH-USD-261225-4000-C - 以太坊看涨期权，行权价 $4,000，2026 年 12 月 25 日到期

其中：

  • C = 看涨期权
  • P = 看跌期权

EVENTS（事件合约）​

OKX 事件合约的金融工具 ID 使用 OKX instruments API 返回的市场 ID。适配器把这些市场表示为 Nautilus BinaryOption 金融工具。

示例：

  • BTC-ABOVE-DAILY-261224-1600-65000 - BTC-ABOVE-DAILY 系列中的事件合约市场。

常见问题​

问：如何知道该用哪种合约类型？ 答：线性与反向金融工具的符号不同。公共 Python 配置不暴露合约类型过滤器，因此所选衍生品类型下 适配器会把两者都加载。

问：如何加载事件合约？ 答：使用 OKXInstrumentType.EVENTS。公共 Python 配置会加载全部可发现的事件合约系列， 不提供系列过滤器。

零售价格改进（RPI）​

零售价格改进（RPI）适用于这些任务：

  • 消费 OKX 合并后的自然与 RPI 深度。
  • 挂出 RPI maker 订单。
  • 让标准订单吃掉 RPI 流动性。

适配器把这些特性映射到 Nautilus 现有的订单簿、订单与生命周期类型上。RPI 路由是选择加入的， 标准订阅与订单保持原样。

RPI 行情数据​

给 subscribe_book_deltas 或 request_book_snapshot 传入 params={"rpi": True}，即可使用 公共 books-rpi 频道或 GET /api/v5/market/books-rpi。该馈送把自然数量与可用于执行的 RPI 数量合并。

每个原始深度档位的线上形态为 [price, totalQty, nonRpiQty, count]：

线上字段Rust 类型含义
priceDecimal价位。
totalQtyDecimal自然数量加可用的 RPI 数量。
nonRpiQtyDecimal无 RPI taker 权限时可见的数量。
countu64该价位聚合的订单数。

Nautilus 的 OrderBookDeltas 与 OrderBook 用 totalQty 作为档位数量。类型化原始模型保留 nonRpiQty。两者之差即可用的 RPI 流动性。

WebSocket 快照与更新保留 seqId 与 prevSeqId。发出的 delta 以 seqId 作为序列号。数据 客户端将每条更新的 prevSeqId 与最后接受的 seqId 比对，两者不要求递增一。不匹配即启动 订单簿恢复。发出在 prevSeqId: -1 的快照被接受后恢复。

标准 OKX 增量簿频道带 prevSeqId 时，适配器应用同样的衔接规则。books-rpi 没有校验和。

WebSocket 订阅中 rpi=True 直接选择 books-rpi，跳过深度或 VIP 频道选择。REST 快照中请求 深度作为 sz 传入。OKX 默认每侧一档，最多接受 400 档。

  • WebSocket：OKXWebSocketClient.subscribe_book_rpi 与 unsubscribe_book_rpi。

RPI 最小名义价值​

RPI maker 订单必须同时满足金融工具的 minSz 和 RPI 最小名义价值：

  • SWAP 与 FUTURES：10,000 USD。
  • SPOT：1,000 USD。
  • EVENTS：豁免 RPI 最小名义价值。

低于适用名义价值门槛的订单，OKX 以 54051 拒绝。执行客户端对被拒绝的下单发出 OrderRejected。

改单只要包含 newSz，无论是否带 newPx，OKX 都会重新检查。被拒绝的改单使原订单继续有效。 适配器发出 OrderModifyRejected，并停止将该改单视为待处理。仅改价的改单不触发该检查。 批量下单或批量改单中的每个子订单独立检查。

该规则于 2026 年 8 月 18 日在生产环境生效时已挂在簿上的订单被豁免（老人老办法）。非 RPI 订单不受此名义价值规则约束，包括带 rpiTakerAccess: true 的订单。满足 minSz 的订单仍 可能无法通过 RPI 最小名义价值检查。

RPI 响应与生命周期​

私有订单消息同时解析 ordType: rpi 与迁移别名 ordType: elp。未成交的 RPI 下单可能在私有 订单频道上首次出现时就是 state: canceled，且 accFillSz 为零或空。此时适配器直接发出 post-only 订单拒绝，不先发接受事件。回退原因写作 RPI order canceled before acceptance。 RPI 价格未通过间距规则且 rpiPxRound 为 false 时，OKX 可能走这条路径。订单报告中 RPI 订单 表示为 post_only=True 的 Nautilus LIMIT 订单。

用 get_account_instruments 读取类型化的 OKXRpiPermission 值：

  • Disabled 对应 rpi: "0"。
  • Enabled 对应 rpi: "1"，不代表有挂 RPI 订单的权限。
  • Permitted 对应 rpi: "2"，有挂 RPI 订单的权限。

公共金融工具端点不返回账户权限。原始费率响应以可选 Decimal 暴露 rpiMaker。空值表示 RPI 不适用。

过渡期内响应可能同时包含 RPI 与 ELP 字段名。适配器优先读取 rpi 与 rpiMaker，把 elp 与 elpMaker 作为响应别名读取，发送时只使用 RPI 名称。原始成交消息中 source: "1" 表示 RPI 订单。

RPI 排除项​

适配器有意排除以下事项：

  • 不暴露废弃的 books-elp 订阅，也不发出 ordType: elp。
  • 不把公开的 RPI 间距阈值当作权威客户端校验依据。
  • 不对 algo 订单应用 RPI 控制项。常规 HTTP 订单路径对价差订单的 RPI 控制项直接拒绝。
  • 不随 RPI 支持引入通用的 post-only 回放去重。

期权与事件合约上，OKX 忽略 rpiPxRound。

参见 OKX RPI 迁移 changelog 与 RPI 计划指南。

WebSocket 订单标识​

OKX WebSocket 订单操作使用 instIdCode（数字金融工具标识），而不是字符串 instId 参数。 适配器从启动时获取的金融工具定义中解析 instIdCode，并在会话期内缓存。所需 instIdCode 不在缓存中时，订单提交以明确的错误失败。

账户激活​

注意

仅当 OKX 以错误码 54109 拒绝 Crypto-USDC 订单后，才调用 OKXHttpClient.activate_feature("1") 启用 USDC 订单簿交易，然后重新提交订单。 激活在主账户与其子账户之间共享，任一账户成功一次即可覆盖全部。适配器从不隐式激活账户。

Client order ID 要求​

OKX 要求 client order ID 只含字母和数字，且不超过 32 个字符。连字符（-）会被拒绝，因此在 策略配置中设置：

超过 32 个字符的 Nautilus client order ID 同样会被拒绝。需要 UUID 形式的标识符时，把 use_uuid_client_order_ids=True 与 use_hyphens_in_client_order_ids=False 组合使用， 使生成的值符合 OKX 限制。

拒绝原因​

OKX 以错误码拒绝订单、改单或撤单请求时，OrderRejected、OrderModifyRejected 或 OrderCancelRejected 上的 reason 形如 OKX error <code>: <message>，例如 OKX error 51000: Parameter instId error。没有消息的 WebSocket 响应只产生 OKX error <code>；带 subCode 的追加 (subCode=<code>)。已被接受但随后失败的条件订单 只报告代码，例如 OKX error 51008，因为 OKX 只发送 failCode。

适配器在联系 OKX 之前发出的拒绝，例如本地校验失败，携带适配器自己的消息，不带 OKX 错误码。

持仓模式​

OKX 的衍生品交易支持两种持仓模式：

  • 净额模式（netting）：每个金融工具一个持仓，买卖订单相互抵消。这是默认模式，也是推荐给 多数交易者的模式。

备注

持仓模式作用于整个账户。通过 OKX 网页或 App 界面设置，或调用 OKXHttpClient.set_position_mode。 客户端配置不负责设置它。两种模式下适配器都会报告持仓：净额模式按带符号数量推导持仓方向， 多空模式使用 OKX 报告的 posSide。

条件订单架构​

条件订单（OKX algo 订单）的命令走 HTTP，状态更新走 WebSocket：

  • 提交：HTTP /api/v5/trade/order-algo 返回即时确认。
  • 状态更新：WebSocket 业务端点（/ws/v5/business）。止损与触及类订单用 orders-algo， 移动止损用 algo-advance，两者都提供实时更新。
  • 撤销：algo 父单仍活动时期通过 HTTP 撤销。

触发生成的子单成为权威订单后，撤销与修改使用它的订单 ID 和常规 WebSocket 路由。Nautilus 订单标识保持不变。

orders-algo 频道只发更新，algo-advance 在订阅时还会发一份快照。适配器在传输重连之间 保留已跟踪订单的上下文，并对回放的 advance-algo 快照去重。冷启动与漏更新的恢复仍由 REST 对账负责。

修改条件订单​

modify_order 通过 HTTP amend-algos 修改待触发的止损与触及类订单。

  • 保留条款：未提供的价格与触发源保持不变。

  • 确认：必须由 algo 流确认变化后的条款，才发出 OrderUpdated。仅收到确认响应不发更新。
注意

待处理的修改需要已跟踪的会话上下文。重启后恢复的订单或缺少该上下文的订单，本地直接发出 OrderModifyRejected。移动止损 algo 的修改同样在本地发出 OrderModifyRejected。

风险管理​

强平与 ADL 事件处理​

OKX 适配器能识别交易所发起的风险管理事件：

  • 强平预警：instrument_types 包含 MARGIN、SWAP、FUTURES 或 OPTION 时，执行 客户端以 instType=ANY 订阅 liquidation-warning。OKX 报告有持仓临近强平时记 warning。 这只是早期预警：消息到达时持仓可能已被强平，且适配器只把它呈现为日志消息，不是面向策略 的事件。
  • 强平订单：交易所强平持仓时，适配器识别强平类别，并带订单详情记 warning。这些订单继续 走正常的订单与成交管道。
  • 自动减仓（ADL）：OKX 为对冲对手方强平而平掉你的持仓时，适配器识别 ADL 事件，并带持仓 详情记日志。

强平订单与 ADL 的识别依据订单记录的 category 字段。可识别的取值：

category含义
full_liquidation整仓强平。
partial_liquidation部分强平。
adl自动减仓平仓。
delivery合约到期交割。
normal / 其他值常规订单流。

类别识别在两条路径上都会运行：

  • WebSocket orders 频道（实时订单与成交更新）。
  • HTTP GET /api/v5/trade/orders-history（用于对账与冷启动 mass status）。
信息

强平与 ADL 事件以 WARNING 级别记录，详情包括订单 ID、金融工具与状态。强平预警则记录持仓 方向、大小、保证金率、标记价格与保证金模式。把这些日志纳入风险管理流程监控。

适配器把这些交易所生成的订单以 OrderStatusReport 与 FillReport 消息转发，持仓更新以 PositionStatusReport 消息发送。由于分派时这些订单未被跟踪，该路径不会直接发出归属于策略的 订单事件。

OKX 适配器支持交易期权（OPTION 金融工具类型），与其他衍生品有些差异。OKX 期权是以标的 加密货币结算的反向合约。完整 API 细节见 OKX 期权交易文档。

支持的订单类型​

只支持限价类订单。OKX 不允许期权使用市价单。

订单类型支持备注
LIMIT✓标准限价单。
MARKET-在到达 API 之前被适配器拒绝。
MARKET_TO_LIMIT-在到达 API 之前被适配器拒绝。

期权 Greeks​

OKX 在 opt-summary 频道上并行发布两套 Greeks：

  • Black-Scholes（BLACK_SCHOLES）：以美元计价的 Greeks。与 Deribit 和 Bybit 适配器 使用的惯例一致。
  • 价格调整（PRICE_ADJUSTED）：以标的币单位计价的 Greeks。与 OKX 原生合约惯例一致。

默认情况下，适配器在每个 opt-summary tick 上发出两套。每个发出的 OptionGreeks 带 convention 字段，取 GreeksConvention.BLACK_SCHOLES 或 GreeksConvention.PRICE_ADJUSTED， 接收方可以按消息分支处理。

要收窄数据流，在订阅时传 params["greeks_convention"]：

  • 单个字符串："BLACK_SCHOLES" 或 "PRICE_ADJUSTED"（不区分大小写）。
  • 字符串列表：["BLACK_SCHOLES", "PRICE_ADJUSTED"]。
  • 省略：适配器发出两套。

未知条目记 warning 后跳过。若请求的条目全部未知，适配器回退为发出两套。

# Default (both conventions, receiver branches)
self.subscribe_option_greeks(instrument_id)


def on_option_greeks(self, greeks: OptionGreeks) -> None:
    if greeks.convention == GreeksConvention.BLACK_SCHOLES:
        self._handle_bs(greeks)
    else:
        self._handle_pa(greeks)
# Single-convention narrowing
self.subscribe_option_greeks(
    instrument_id,
    params={"greeks_convention": "PRICE_ADJUSTED"},
)
# Explicit list (equivalent to the default when both are listed)
self.subscribe_option_greeks(
    instrument_id,
    params={"greeks_convention": ["BLACK_SCHOLES", "PRICE_ADJUSTED"]},
)
备注

数据引擎按 instrument_id 对期权 Greeks 订阅去重。同一节点上两个 actor 以不同的单一 convention 订阅同一金融工具时，只有第一个订阅到达适配器，第二个 actor 得到第一个 actor 的 convention 集合。变通办法：任一 actor 不带 params（或带完整列表）订阅，接收两路数据后按 greeks.convention 本地过滤。

持仓 Greeks​

OKX 持仓负载包含持仓级 Black-Scholes Greeks（delta_bs、gamma_bs、theta_bs 与 vega_bs）。适配器的标准 PositionStatusReport 不暴露这些字段。上文描述的 opt-summary 流提供适配器暴露的按金融工具 Greeks。

限制​

  • 期权的 reduce-only 订单被适配器拒绝，因为 OKX 对期权不支持该指令。
  • 持仓方向默认 Net。

未确认的提交​

OKX 把 50004 与 51149 定义为未知请求结果。 适配器让这些提交保持未决，但对账检查耗尽后，默认执行策略仍可本地裁决它们。OKX 不会自动启用 提交保留。

要保留未确认的提交（包括没有任何响应的），在构造节点时选择现有的引擎策略：

use nautilus_live::{
    config::LiveExecutionEngineConfig,
    execution::submission::SubmissionRecoveryPolicy,
};

let exec_engine = LiveExecutionEngineConfig {
    submission_recovery_policy: SubmissionRecoveryPolicy::RetainUnresolved,
    ..Default::default()
};

这是节点执行引擎的策略，不是 OKX 客户端设置。恢复查询始终有界。查询耗尽时发布一次 SubmissionRecoveryExhausted，并保留提交身份以供后续的权威证据匹配，不重新提交订单。确认与 查询预算规则见提交恢复。在节点 delay_post_stop 边界仍未决的保留提交，会在拆除后产生 不完整恢复的关闭错误。该策略不改变 已受理订单上命令的超时裁决，不提供崩溃可持久的恢复，也不能证明持仓已平。

确定性仿真测试​

OKX 是适配器 DST 契约的参考实现， 适配器开发者指南要求受维护的适配器 满足该契约。本节记录经过审计的 OKX 切片：静态闸门覆盖的文件、其余部分的排除理由，以及 dst 测试证明的运行时切片。

受审文件​

受审的 OKX DST 路径生产文件把影响状态的时钟读取与定时器路由到 DST 缝（seam），并按顺序重连与 批量退订订阅命令。静态闸门覆盖 crates/adapters/okx/src 中的这些文件：

  • book：mod.rs、recovery.rs、sync.rs
  • common：parse.rs、task.rs
  • 顶层：config.rs、data.rs、execution.rs
  • http：client.rs、models.rs、query.rs
  • websocket：client.rs、dispatch.rs、handler.rs、messages.rs、parse.rs、 subscription.rs
注意

仅靠静态覆盖不能确立运行时资格：这些文件也服务于已证明运行时切片之外的路径。

排除文件​

其余非 Python 的 OKX 生产文件保持排除，因为它们不承载 DST 路径的状态、时钟、RNG、任务或传输 面：

  • 模块声明：lib.rs、common/mod.rs、http/mod.rs、websocket/mod.rs。
  • 纯场所类型：common/enums.rs、websocket/enums.rs、http/error.rs、 websocket/error.rs、common/models.rs。
  • 纯表与确定性映射：common/urls.rs（端点表）与 common/consts.rs（纯谓词、校验器， 以及 wire 值与频道解析器；其中的 AHashSet 仅用于 contains 的重试查找，从不迭代）。
  • 确定性辅助：common/credential.rs，其 HMAC 对调用方提供的时间戳签名，凭据解析只在构造 时读取配置或声明的环境；common/failure.rs 是纯错误分类。
  • 仅构造接线：factories.rs。
  • 仅测试或占位：common/testing.rs、http/parse.rs。

check-dst-conventions 把这份理由记录在 ADAPTER_PATHS 旁边。文件若新增 DST 路径的运行时 逻辑，需重新审计。src/python/ 下的七个文件按仓库范围的 Python/FFI 政策保持排除，不属于本 审计（见 Python 与 FFI 不在 DST 范围）。

已证明与未证明的切片​

crates/adapters/okx/tests/integration/dst.rs 中的 Madsim 专项测试证明这个切片：

  • 订阅字节：公共 WebSocket 报价、成交与簿；业务 WebSocket K 线。
  • 重连顺序：多金融工具报价按主题顺序重连。重连还会清空 data.rs 中的报价与资金费率缓存， 使新一代不会复用旧值。
  • 登录帧：key、passphrase 与由模拟挂钟派生的签名。
  • wire 字段：单笔下单、改单与撤单；algo 下单与撤单；按输入顺序的批量下单。

完整的请求到 wire 到领域的新鲜进程比对留在下游 DST 工具链。以下条目共享 DST 门面与规范闸门， 但尚未证明：

  • 其他公共频道：ticker、资金费率、指数行情、期权汇总、其他簿深度，以及其他 K 线粒度。
  • 私有数据流。
  • 批量撤单、批量改单与撤销，以及价差订单。
  • HTTP 报告与对账路径。
