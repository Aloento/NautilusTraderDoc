Shell 脚本

本页定义何时创建 shell 脚本，以及如何命名、编写、调用与测试它。默认使用 Bash。 只有当受支持的调用方确实无法依赖系统装有 Bash 时，才用 POSIX sh。

本策略适用于仓库中所有 shell 文件，包括 scripts/、scripts/ci/、 .pre-commit-hooks/ 与各组件目录。

何时写脚本​

添加脚本前，先搜索是否已有脚本、Make 目标或已安装的工具提供该行为。 当脚本能让过程化逻辑拥有单一的可测试、可 lint 的事实来源时，再添加脚本。

位置负责内容下放
GitHub Actions事件、权限、矩阵、runner、secrets 与 hosted action多步 shell 行为
Makefile可发现的任务、依赖、变量与并发限制非平凡的控制流
Shell 脚本校验、可复用的命令序列、重试与转换工作流编排与构建依赖管理

下列情形优先用脚本：

  • 某命令序列被多个工作流、Make 目标或开发任务使用。
  • 内联的 GitHub Actions 步骤含有值得在工作流之外测试的分支、循环、重试或失败处理。
  • Make recipe 的过程化逻辑多到引号、错误传播或平台行为难以评审。
  • 重复的维护或发布任务能从 ShellCheck、shfmt 与聚焦测试中受益。

命令简短、只用一次、放在调用方里更清晰时，保持内联。不要仅为多出一个文件去包装 一条稳定的命令。

从 GitHub Actions 抽离逻辑时，${{ github.ref }} 这类表达式、权限、secret 选择与 runner 选择留在工作流里。普通值通过参数或环境变量传给脚本。脚本的退出状态必须 仍是该步骤的退出状态。

选择 shell 与扩展名​

扩展名标识 shell 语言，不表示文件是否可执行或可 source。

扩展名解释器用途
.bashBash新脚本与可 source 的 Bash 文件的默认选择。
.shPOSIX sh仅当受支持的调用方确实有不依赖 Bash 运行的要求。

.bash 文件用 #!/usr/bin/env bash，.sh 文件用 #!/usr/bin/env sh。 保留 shebang，即使 Make 或 GitHub Actions 通过 bash 或 sh 调用该文件。 工具与直接调用方靠它识别解释器。

常规的开发、Make 与 CI 脚本优先用 Bash，因为仓库本就依赖它，且它的特性让 非平凡的 shell 代码更清晰。这些特性包括 pipefail、[[ ... ]]、数组、 进程替换与函数局部变量。

小型引导或包装脚本可能有必须不依赖 Bash 的受支持接口，这类脚本才用 POSIX sh。 要在目标的 /bin/sh 下测试该脚本。仅凭语法简单证明不了 POSIX 兼容。

既有文件名早于这条扩展名策略，所以有些 .sh 文件实际是 Bash。以它们的 shebang 为事实来源。不要仅为改扩展名而重命名既有脚本。该策略适用于新文件，以及已经更新 所有调用点与文档的成范围重命名。

定义可移植目标​

脚本必须支持其调用方运行的每个平台。除非用途指明更窄的目标，否则按 Linux、 macOS 以及经由 Git Bash、MSYS2 或 WSL 的 Windows 来写。

默认的语言下限是 Bash 3.2，因为受支持的 macOS 系统都有它。除非每个调用方都 配置了更新版本，否则避免 Bash 4+ 特性。常见的 Bash 4+ 特性与可移植替代：

特性Bash 版本可移植替代
关联数组（declare -A）4.0+文件、简单数组或函数
readarray / mapfile4.0+while read 循环
${var,,} / ${var^^}4.0+用 tr 做大小写转换

仅 CI 使用的脚本，当所有工作流调用方都保证该环境时，可以用更新的 Bash 版本或 平台专属工具。在依赖该约束的代码旁注明。scripts/ci/ 下的路径本身不会让脚本 变成 Linux-only，因为 CI 也使用 macOS 与 Windows runner。

系统工具​

优先选 GNU 与 BSD 工具都支持的选项。没有公共写法时，探测能力或操作系统， 并实现两种形式。

操作GNU 写法BSD 或 macOS 写法可移植做法
sed 原地修改sed -ised -i ''用备份后缀如 sed -i.bak，然后删除备份。
文件大小stat -c '%s'stat -f '%z'尝试或选择受支持的写法。
SHA-256sha256sumshasum -a 256探测命令，并保持输出处理一致。
规范路径readlink -f无公共写法避免使用，或从已知目录用 pwd 解析。
扩展匹配grep -P无公共写法grep -E 能表达同样模式时用它。
纳秒时间date +%N无公共写法用已有的运行 ID 或 $RANDOM 做缓存失效。

对路径与展开加引号，防止空格改变参数边界。不要假定文件系统路径区分大小写。 先根据脚本所在位置（而非调用方的工作目录）解析出仓库根，再使用仓库相对路径。

只用文档化的开发环境或 runner 配置所安装的命令。确需可选命令时，用 command -v 检查，并说明如何安装或替代。仓库通过 .gitattributes 以 LF 行尾存储文本， 不要添加平台专属的行尾。

脚本的位置与命名​

  • 通用的开发与维护命令放 scripts/。

  • 工作流专属的构建、测试、发布与校验命令放 scripts/ci/。

  • 由 pre-commit 调用的仓库检查放 .pre-commit-hooks/。

  • 组件专属的脚本在移入 scripts/ 会掩盖其归属时，留在组件旁边。

  • scripts/ 下与组件目录中使用小写 kebab-case。回归测试脚本命名为 test-<script-name>.bash 或 test-<script-name>.sh，让被测的一对文件保持在一起。

  • .pre-commit-hooks/ 下使用小写 snake_case，并沿用现有的 check_* 与 test_check_* 命名族。

每个脚本聚焦一个任务；新逻辑与既有脚本职责相同时，扩展它而不是新建。

以可靠执行为目标组织脚本​

独立的 Bash 脚本以这两行开头：

#!/usr/bin/env bash
set -euo pipefail

独立的 POSIX sh 脚本用 set -eu。POSIX 没有定义 pipefail，失败必须传播时 要显式检查管道的行为。脚本无法使用这些选项时，说明是哪段具体的控制流让某个 选项不安全。

遵循以下要求：

  • 改变状态之前校验必填参数与环境变量。无效输入时打印简明的用法说明并以非零退出。
  • 参数展开要加引号。参数列表用 Bash 数组，不要拼接命令字符串，也不要使用 eval。
  • 调用方需要捕获结果时，机器可读的输出走标准输出，诊断信息走标准错误。
  • 常规状态输出不以句号结尾。输出是完整的解释性或诊断性句子时保留标点。
  • 用 mktemp 创建临时文件，用 trap 注册清理，且清理只限定在脚本创建的那些路径。
  • 重试要有上限，报告最终的失败；请求的操作没有完成时返回非零状态。
  • 不要打印 secret，也不要在凭据附近启用命令跟踪。secret 通过环境或工具支持的 secret 输入传入。
  • 只在命令本身讲不清约束或行为时才写注释。

用户或工具以 ./path 方式调用时，给独立脚本加可执行权限。可 source 的文件不需要。 优先在子进程中执行脚本；只有调用方必须共享其函数或 shell 状态时才 source 文件。

可 source 的 Bash 文件不得调用 exit，也不得改动调用方的 shell 选项。 函数返回错误，由调用方决定错误策略。解析源文件位置时用 ${BASH_SOURCE[0]} 而不是 $0。

脚本需要多个函数时：

  1. 先定义 main。
  2. 被调用的函数放在调用方下方。
  3. 所有定义完成后再调用 main "$@"。

这样任务在文件顶部一目了然，同时保证执行开始前每个函数都已存在。

与 Make 和 GitHub Actions 集成​

Make 目标提供开发者运行的稳定、可发现的命令。目标依赖、构建变量与并发限制留在 Makefile，然后以显式解释器调用脚本。例如 check-generated-drift 目标把它的 过程化工作下放给 scripts/ci/check-generated-drift.bash。

GitHub Actions 通过具名环境变量提供工作流上下文，并在可行处调用与本地相同的脚本。 构建工作流就遵循这条边界：它掌控 Python 矩阵条件与 TARGET_DIR， 然后调用 scripts/ci/check-generated-drift.bash。

脚本同时也是本地命令时，GitHub 专属的输出文件（如 $GITHUB_OUTPUT 与 $GITHUB_ENV）留在工作流边界。专职 GitHub Actions 的脚本，在其声明的用途就是 这层集成时，可以写这些文件。

格式化与 lint​

pre-commit 配置用 shfmt 格式化 shell 文件：两空格缩进、case 分支缩进、 一致的重定向间距、Bash 解析器。随后 ShellCheck 检查引号、展开、控制流、 可移植性与常见命令错误。工具版本与选项以 .pre-commit-config.yaml 中固定的 钩子为事实来源。

对确切改动的脚本运行两个钩子：

prek run shfmt --files scripts/ci/test-wheel.bash
prek run shellcheck --files scripts/ci/test-wheel.bash

shfmt 原地更新文件，先审阅它的改动再运行 ShellCheck。ShellCheck 从 shebang 选择语言，因此带 #!/usr/bin/env sh 的 .sh 文件会接受 POSIX 检查， 即便格式化器用的是通用的 Bash 解析器。

ShellCheck 抑制只放在最窄的适用行上。代码讲不清约束时，在旁边补一句原因。 不要为了压住一个脚本而在全仓库禁用某项检查。

仓库还拒绝没有 shebang 的可执行文件、混合行尾、行尾空白与未解决的合并标记。 这些检查与 ShellCheck 互补，不能替代运行时测试。

测试行为​

运行能覆盖改动分支与失败路径的最小测试。对能独立于工作流回归的逻辑， 添加配套的 shell 测试。这包括解析、多分支决策、重试与清理、策略检查， 以及实质性的外部副作用。

领域级的套件可以覆盖协同工作的多个脚本。薄包装若被该套件调用且行为已被证明， 就不需要一对一的测试。

每个配套测试：

  • 在 mktemp -d 下创建隔离状态，退出时删除。
  • 通过临时 PATH 提供伪造的外部命令，而不是改动生产代码。
  • 用有区分度的输入，并对输出、退出状态与副作用做精确断言。
  • 覆盖成功、无效输入、依赖失败与清理这些存在的路径。
  • 所需的测试命令不可用时直接失败。跳过的"通过"不能验证行为。
  • 经由 make test-scripts 运行，这是 CI 使用的脚本测试清单。

脚本在多个操作系统上都有调用方时，在各方相关的 CI 矩阵上验证平台敏感的改动。 Linux 测试加干净的 ShellCheck 输出证明不了 macOS 或 Windows 的行为。

评审清单​

  • 该行为没有现成的脚本、Make 目标、已安装工具或简单的原生工作流特性可用。
  • GitHub Actions、Make 与脚本各自负责了工作流中正确的部分。
  • 扩展名、shebang、可执行模式与文档化的可移植目标相互一致。
  • 脚本独立于调用方的工作目录运行。
  • 参数、失败、临时文件、重试、输出与 secret 都有显式处理。
  • 针对最终改动文件，聚焦的行为测试、shfmt 与 ShellCheck 全部通过。
  • 每个调用点、工作流路径过滤与文档都使用最终的文件名。
