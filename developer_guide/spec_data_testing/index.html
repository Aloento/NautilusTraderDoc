数据测试规范

使用这份测试矩阵，配合 Rust 的 DataTester actor 验证适配器的数据功能。Python 将其作为内置 actor 暴露，通过 nautilus_trader.testkit.DataTesterConfig 配置；Rust 代码从 nautilus_testkit::testers 导入。用例使用带前缀的 ID（例如 TC-D01），按功能分组。

每个适配器必须通过与其支持的数据类型相对应的那部分测试。

测试组按数据派生程度从低到高排列：先金融工具和原始订单簿数据，再报价、成交、K 线和衍生品数据。 通过第 1-4 组的适配器即视为达到基线数据合规。

适配器特有的数据行为（自定义通道、限流、快照语义等）写在各适配器自己的指南里，不写在这里。

前置条件​

运行数据测试前：

  • 目标金融工具可用，且能通过 instrument provider 加载。
  • 被测数据在交易场所需要鉴权时，通过环境变量设置 API 凭证（{VENUE}_API_KEY、{VENUE}_API_SECRET）。
  • 交易场所若提供 demo/testnet 模式，使用该环境下创建的凭证。演示环境与生产环境的 API key 通常相互独立、 不可互换。用错凭证会导致鉴权错误（如 HTTP 401）。

Python 节点搭建：

使用 nautilus_trader.live.LiveNode。若需在节点构建前注册适配器客户端工厂，调用 LiveNode.builder(...)。

from nautilus_trader.common import Environment
from nautilus_trader.config import LiveDataEngineConfig
from nautilus_trader.live import LiveNode
from nautilus_trader.model import TraderId
from nautilus_trader.testkit import DataTesterConfig

node = (
    LiveNode.builder("TESTER-001", TraderId("TESTER-001"), Environment.SANDBOX)
    .with_data_engine_config(LiveDataEngineConfig(time_bars_build_with_no_updates=False))
    .add_data_client(None, adapter_data_client_factory, data_client_config)
    .build()
)

tester_config = DataTesterConfig(
    client_id=client_id,
    instrument_ids=[instrument_id],
    subscribe_quotes=True,
)
node.add_builtin_actor("DataTester", tester_config)
# Register remaining components, then start or run

Rust 节点搭建（参考：crates/adapters/{adapter}/examples/node_data_tester.rs）：

use nautilus_testkit::testers::{DataTester, DataTesterConfig};

let tester_config = DataTesterConfig::builder()
    .client_id(client_id)
    .instrument_ids(vec![instrument_id])
    .subscribe_quotes(true)
    .build()?;
let tester = DataTester::new(tester_config);
node.add_actor(tester)?;
node.run().await?;

时间戳量纲​

Nautilus 以 Unix 纳秒（UnixNanos）存储 ts_event 和 ts_init。凡是携带这两个字段的数据消息都必须使用该 量纲，不能残留秒、毫秒或微秒。

  • 小于 10^16 的值不可能是合法的 Unix 纳秒时间戳（10^16 ns 约为 1970-01-01 之后 116 天），通常说明适配器 没有把交易场所的量纲转换过来。
  • 转换正确的秒级交易场所时间以 000000000 结尾，仍然算通过：那是精度粗，不是量纲错误。
  • 实时流的 ts_event 应接近会话的挂钟时间。历史请求的结果可以更久远，只要量纲是纳秒就仍然有效。
  • ts_init 是 Nautilus 创建对象时的本地时钟。交易场所时钟超前时，ts_event 略大于 ts_init 是可能的。

以下数据类型（含各自的历史批量数据）的 ts_event 或 ts_init 未通过量纲检查时，DataTester 会发出警告：

  • 金融工具、instrument status 和 instrument close。
  • 订单簿增量和订单簿深度。
  • 报价、成交和 K 线。
  • 标记价格、指数价格和资金费率。
  • 期权希腊值。

on_book 中重建出的订单簿不做检查。产生警告的用例一律按失败处理。

订单簿同步合规​

从交易场所数据流维护订单簿的适配器，必须在交易场所和网络故障下保持输出合法。单元测试和集成测试无法复现 交易场所的时序，因此改动订单簿同步与恢复机制时，既要通过确定性的模型检查，也要针对真实交易场所做实时验证。

此处的实时验证指只观察行情：订阅、请求、注入故障。验证期间不要下单。**暗簿（dark book）**指订阅后 始终收不到数据的订单簿。

订单簿数据流契约​

nautilus_live::book::conformance 中的 BookStreamChecker（由 nautilus-live 的 test-support feature 启用）对每个发出的 OrderBookDeltas 批次应用该契约：

  • 批次以 F_LAST 结束。每个 F_LAST 闭合一个事件组，且每组结束后订单簿都必须通过完整性检查，因为消费者 在这些边界处观察订单簿。
  • 快照组是一个 Clear 后接若干 Add 增量，全部带 F_SNAPSHOT 标志。单独的 Clear 是空快照。
  • 增量组既不带 F_SNAPSHOT 也不带 Clear，且位于快照之后。
  • 当交易场所序列号在单个快照 episode 内单调递增时，每个增量组的序列号应大于前一组。OKX 的 seqId 可能重置； Polymarket、Hyperliquid、Betfair 和 AX Exchange 的订单簿不带交易场所序列号。因此这些交易场所的检查器 跳过该规则，依赖 oracle。
  • 订单簿退订完成后不再发出任何内容。

验证级别​

按改动中风险最高的方面选择级别。级别越高，包含以下各级的全部要求。

级别触发条件方法验收标准
L0 模型任何对 BookSync、BookRecovery 或适配器对其使用的改动针对参考模型做单簿状态机的属性测试，外加植入的回归用例属性测试通过；回退已知修复（如 gap 所有权规则）时会失败
L1 合规任何对已验证过的同步/恢复代码的改动重跑该交易场所的压力测试装置或既有 oracle在既定标准上 PASS，零检查器违规、零暗簿、零无法解释的错误
L2 边界探测边界行为变化（超时、禁用路径、预算耗尽、重试上限）定向边界场景，覆盖每个新的调参极端值所有场景通过；禁用路径保持静默；预算耗尽后到达上限，迟到快照仍能恢复订单簿
L3 竞态探测并发或顺序变化（门控、epoch、重连交互），或任何实时发现的竞态修复独立 oracle 下做故障注入加订阅抖动数十次强制恢复全部完成且零暗簿；上报的竞态场景通过且不再复发
L4 完整验证新的同步/恢复实现L1-L3 加上持续的抖动与重连故障浸泡浸泡全程保持各级标准；恢复延迟有界

L0 属性测试是 crates/live/src/book/sync.rs 中的 schedule_keeps_sync_contract。随改动记录级别、交易场所、 oracle 和结果。实时验证发现的修复从发现它的级别重新开始：重跑必须达到同一标准，不能降低。

故障目录​

无论属于哪个恢复家族，每个适配器都必须产生下列结果：

故障要求的结果
序列号缺口输出在缺口处停止，仅在新鲜快照替换订单簿后恢复。
快照缺失或迟到快照截止时间触发或重试恢复。两次尝试之间接受了快照则结束恢复。
恢复无法启动订单簿保持无主状态，在下一帧再次请求恢复。被拒绝的任务会取消其已认领的 episode。
替换被拒绝恢复重试。分类器判定为永久性的错误跳过预算、直接按上限重试。
重试预算耗尽记录一次错误日志，然后按上限重试直到快照被接受。
恢复中途重连进行中的恢复保留其预算、所有权和写入中的操作，其下一次上限等待立即结束。其他订单簿从新鲜快照重新同步。
恢复期间退订恢复及其挂起写入停止，订单簿不再发出任何内容。

构造手段​

优先构造不同的时序组合，而不是单纯堆消息量。只有当探测能强制出测试套件无法产生的时序（恢复中途重连、快照与 门控开启赛跑、退订与进行中的订阅赛跑）时，它才值得保留。仅靠消息数量不足以支撑一个探测。

手段施压点被证明有效的数字实际捕获的问题
订阅抖动（轮换退订/重订阅，周期性全量切换）恢复发起、门控/epoch 轮换、写入中取消的竞态10-15 分钟运行配 20 秒 tick。数十次（40+）强制恢复且零暗簿无法恢复的重复订阅缺陷（迫使重新设计）
流量冻结（切断隧道约 40 秒）死连接检测、重连重放、重连后恢复每次运行 2-3 次冻结，间隔数分钟验证完全丢包下的重连恢复。尚未捕获缺陷
代理故障注入（按规则丢弃/扣留/切断帧）缺口处理、扣留帧释放、oracle 合规每次运行数千个 oracle 批次（6k+）、逐轮缺口计数超时缩放导致的装置竞态（观测窗口 vs 新默认值）
调参极端值（0 加一个较短的非默认值）禁用截止时间的分支、参数端到端传递每个极端值一次短运行（4-5 分钟）并叠加抖动在线确认了评审发现的零超时修复；验证参数传递
客户端主动重连（公共重连命令，随后继续施压）不动宿主机网络的重连恢复5+ 次连续重连/对账通过验证无宿主机故障下的恢复。尚未捕获缺陷
竞态场景串行重复调度敏感性5+ 次连续通过；确定性装置重复 100 次偶发失败、单次通过掩盖的flake

每个交易场所都要经由其服务的网络位置接入。Polymarket 按地区限制访问；OKX、Lighter、Binance、Hyperliquid 和 AX Exchange 校验直连。长时间运行前先确认该路由能送达交易场所数据：socket 能连上但交易场所可能一直沉默。 交易场所线上永远不产生的分支应放进捕获报文的确定性装置，而不是实时运行。

Oracle​

oracle 是对交易场所真实状态的独立重建，通过 BookStreamChecker::verify 与发出的订单簿比对：

  • 从独立连接或 REST 快照构建，绝不使用适配器自身的状态。
  • 在已对齐的交易场所序列号处比对。无法对齐的样本跳过，不算通过。
  • 快照 episode 在其快照之后的某次比对成功时计为已验证。带 Coverage::Episodes 的装置（如 OKX）在每批到达时 即验证，任一 episode 未验证则整个会话失败。带 Coverage::Samples 的装置（如 Binance）事后按 update ID 匹配 oracle 样本，因此它报告的是 oracle 检查和未匹配样本，而非 episode 覆盖率。

压力测试装置​

压力测试装置是修改订单簿同步与恢复代码时使用的开发工具。它们不属于发布的 crate，也不在 CI 中运行。装置使用的 BookStreamChecker 随 nautilus-live 的 test-support feature 发布，其他测试可以套用同一契约。

使用共享订单簿机制的适配器，其实时装置放在 crates/adapters/<venue>/tests/stress/book_stress.rs，注册为名为 <venue>-book-stress 的测试 target：

[[test]]
name = "okx-book-stress"
path = "tests/stress/book_stress.rs"
harness = false
test = false
required-features = ["examples"]

harness = false 让该 target 自己掌控 runtime 和参数，test = false 使其不进入默认的 cargo test 和 nextest 运行。在 crate 的 dev-dependencies 中加入带 test-support feature 的 nautilus-live。

共享机制是 crates/live/tests/book/stress/ 下的测试源码，各装置通过 path include 将其编译进来：

#[path = "../../../../live/tests/book/stress/mod.rs"]
mod stress;

共享模块负责运行装置，交易场所只需实现 StressVenue 提供自己的部件：

  • 一个 WireCodec，把每个交易场所帧分类为订单簿快照、订单簿更新或退订确认。它在应用任何故障之前先把帧记入 oracle。它还能改写帧以植入序列缺口或带内不匹配，并对适配器的订阅返回交易场所拒绝。
  • 代理路由、数据客户端配置，以及任何额外代理路由（如 REST 快照代理）。
  • 每个发出批次的 oracle 比对、订单簿健康的判定条件，以及启动自检。
  • 针对 Session 编写的场景。

FaultProxy 将适配器的 WebSocket 流量转发给交易场所。若某路由的上游 URL 不是 WebSocket URL，它以裸 TCP 转发 CRLF 分隔的行。行路由只提供代理地址，交易场所的 WireCodec::connect 自行打开上游连接（例如经 TLS）。

代理按订单簿应用 Fault 规则（丢弃快照或更新、篡改、扣留、静默、退订时切断、拒绝订阅），并支持连接级的切断 与冻结。Session 让每个发出的批次经过 BookStreamChecker 和 oracle，等待订单簿自愈。关闭时检查所有 socket 和重连句柄均已释放。

各装置接受同一组参数，交易场所可另加自己的参数。--help 会列出：

参数含义默认值
--scenario NAME要运行的场景。churn
--timeout SECSbook_snapshot_timeout_secs。0 禁用快照截止时间。10
--rounds N压力轮数。交易场所默认值

显式运行装置，并剥离适配器环境变量：

CARGO_BUILD_JOBS=16 bash scripts/strip-adapter-env.bash \
  cargo test -p nautilus-okx --features examples --test okx-book-stress -- --timeout 10 --rounds 18

Betfair 只向已登录账户推送行情，因此其装置需在设置 Betfair 凭证后运行。参见 Live recovery validation。AX Exchange 的行情同样需要 鉴权，因此其装置从环境读取 sandbox 凭证，且不经包装脚本直接运行。

装置向 stderr 每个事件写一行，行首是固定单词：

行首含义
START交易场所和参数。
CHECK启动自检或场景探测通过。
ROUND一个压力轮结束，附计数器。
SHUTDOWN会话干净停止，附计数器和 oracle 覆盖率。
PASS运行完成。永远是成功运行的最后一行。
FAIL某检查失败或任一线程 panic。进程以状态码 1 退出。

截止时间失败时会报告每个代理路由收到的交易场所帧，以区分路由静默与适配器故障。

自检：harness = false 的 target 无法运行 #[test] 函数，因此交易场所要在任何交易场所流量发生前，于 StressVenue::self_check 中证明自己的报文解析和 oracle。共享代理、参数解析和裸订单簿在 nautilus-live 的 book 测试 target 中带有单元测试，用 cargo nextest run -p nautilus-live --features test-support --test book 运行。

装置文档：在适配器的集成指南中添加 Live recovery validation 标题，写明其检查项、注入的故障、运行命令、 场景、参数和所需端点。OKX、Binance、Lighter、Polymarket、Hyperliquid、Bybit、Betfair 和 AX Exchange 提供装置。

带内验证​

交易场所若发布订单簿校验和或哈希，就对其进行验证，不匹配按缺口处理。无需外部 oracle，即可发现序列检查漏掉的 覆盖数据中的损坏。

  • Kraken：启用 validate_l2_checksum 和 validate_l3_checksum 时（两者均为默认），验证每条现货 L2 book 和 L3 消息的 CRC32 校验和。
  • Polymarket：验证携带哈希及其完整原像的每个订单簿快照上的哈希。参见 book snapshot validation。
  • OKX：books 帧的 checksum 为零，验证因此改为依赖 oracle。

TC-D73：退役清理​

字段值
前置条件某 actor 拥有交易场所支撑的订阅；两个 actor 共享一个内部聚合的 K 线。
操作先退役第一个 actor，再通过 trader 退役第二个 actor。
事件序列on_dispose 完成；退订命令已发出；actor 已注销。
通过标准第一次退役后共享数据保持活跃；最后一次退役释放保留的路由，且不留退役 actor 的处理器。
跳过条件不适用。

第一个 actor 退役后，共享 K 线必须保持活跃；最后一个 actor 退役后必须停止。

注意事项：

  • DataTesterConfig 不覆盖多 actor 退役场景。需手动创建两个 actor，再通过 Python Controller.remove_actor 或 Rust Trader::remove_actor 移除。
  • 若 on_dispose 失败，actor 必须保持注册且订阅完好，使后续退役能释放订阅，且不再调用失败的钩子。
  • on_stop 或 on_fault 失败不得阻塞退役：必须仍能从对应的过渡状态完成处置和注销。

TC-D74：DeFi 共享池需求​

字段值
前置条件一个 DeFi 数据客户端。两个 actor 以相同或部分重叠的订阅类型订阅同一个池。
操作以每种顺序退役或退订其中一个 actor，再处理另一个。
事件序列第一次释放不向客户端发出共享类型的退订；最后一次释放执行退订并停止池更新器。
通过标准在最后一次释放之前，池事件持续送达剩余的 actor 和 profiler；之后不再有任何事件。
跳过条件适配器不提供 DeFi 池订阅。

需覆盖以下重叠情形：

  • 两个 actor 使用同一订阅类型，按任一顺序退役。
  • SubscribePool 与每个更窄的类型（swap、流动性更新、fee collect、flash 事件）组合，按两种顺序退订。 只要任一订阅仍在，更窄的事件过滤器必须保持生效。
  • 两个数据客户端订阅同一个池。每个客户端各自维护自己的需求，池更新器在两者都释放前保持活跃。

注意事项：

  • DataTesterConfig 不覆盖 DeFi 池订阅。需手动创建 actor。
  • 一个 actor 的重复退订不得释放另一个 actor 的需求。

TC-D75：DeFi 引导取消​

字段值
前置条件一个 DeFi 数据客户端。池中金融工具不在 cache 里，因此订阅会请求池快照。
操作先订阅，在池定义到达前释放最后一个持有者，然后再次订阅。
事件序列发出两次快照请求；第一次的响应在第二次订阅之后才到达。
通过标准引擎丢弃第一次响应；只有对应当前请求的响应会安装 profiler。
跳过条件适配器不提供池快照。

注意事项：

  • 只有池不在 cache 中时，第二次订阅才会请求新快照。一旦第一次请求的池定义到达，后续订阅会直接用缓存的池 构建 profiler，因此该用例需要延迟响应。
  • 引擎重置或断开连接同样会取消进行中的引导。之后到达的响应不得安装 profiler。
