设计原则

本页定义指导 NautilusTrader 设计、实现与评审的原则、策略与取舍。 架构描述的是组件与运行时结构。

这些策略并不宣告每条既有路径都已然符合。各具体指南描述现状与限度。 运行时一致性契约把选定要求映射到源码、代表性检查与 实现限度。

设计优先级​

设计决策大致按以下顺序权衡这些质量属性：

  • 可靠性
  • 性能
  • 模块化
  • 可测试性
  • 可维护性
  • 可部署性

性能改进必须保留关键不变式及其要求的验证。可测试性与可维护性支撑可靠性， 可部署性影响安全上线、配置与恢复。优先级排序不意味着这些品质可以取舍。

数据完整性与失败​

对交易操作，NautilusTrader 把数据完整性置于可用性之上。算术与数据处理边界 返回错误或 panic，而不是静默接受可能影响交易决策的非法值。

非法操作​

遇到下列情形，系统按 API 契约快速失败——返回错误或 panic：

  • 时间戳、价格或数量的运算超出有效范围导致的算术上溢或下溢。
  • 反序列化中的非法数据，包括行情数据或配置中的 NaN、无穷值、越界值。
  • 类型转换失败，例如只接受正值之处（时间戳、数量）出现负值。
  • 价格、时间戳或精度值的畸形输入解析。

在交易系统中，一个错误的价格、时间戳或数量可能传导成：

  • 错误的仓位规模或风险计算。
  • 以错误价格发出的订单。
  • 产生误导性结果的回测。
  • 无声的财务损失。

在非法操作处失败带来：

  • 无静默损坏：受检输入在非法值传播之前就被拒绝。
  • 即时反馈：调用方在契约被违反的那一点收到错误，或进程终止。
  • 诊断上下文：错误与 panic 消息指明被拒绝的操作或值。
  • 确定性行为：在确定性顺序与配置下，同样的非法输入产生同样的失败。 非确定性输入仍可能改变结果。

预期的网络、存储、业务校验与用户输入失败有明确的错误出口。不可恢复的不变式 违规则在非法状态传播之前停止该操作或进程。panic 与可失败 API 的行为定义见 Rust 错误契约。

失败遏制​

停止完整性已无法确立的最小范围，前提是其余系统能安全继续。隔离成立时， 被拒绝的输入或失败的操作不必停下无关组件。不可信的共享状态可能要求停止节点。 遏制要遵循该 API 的失败契约与已证实的隔离边界，不能假定某组件能从任意 panic 中恢复。

停止进程不会取消交易场所上的活动订单，也不会消除敞口。恢复必须先确立交易场所状态， 再决定哪些后续动作是安全的。

可执行不变式​

NautilusTrader 在高保障实践上对关键路径渐进采用。可执行不变式验证行为是否 符合业务要求：

  • 识别高影响组件（包括核心领域类型以及风险与执行流程），用平实的语言陈述其不变式。
  • 把这些不变式固化为可执行检查（单元测试、属性测试、fuzzer 与静态断言），在 CI 中运行。
  • 通过类型与显式的失败契约强制所有权与状态不变式。形式化工具的收益配得上成本时再引入。
  • 要求集成方保留既有关键路径的不变式，并为其引入或改变的不变式补充可执行覆盖。

这一方式给高风险流程额外审视，而不把同样的保障成本摊到每条路径上。

延伸阅读：High Assurance Rust。

消息不可变性​

消息（请求、响应、事件与命令）创建后不可变。其字段在消息余下的生命周期中 保持不变。由这一不变式派生的所有权规则见 消息总线：消息完整性。

这一不变式保护系统依赖的若干性质：

  • 稳定的输入：每个消费者看到的消息载荷都相同。重放一个序列时，能还原出 最初的逻辑输入，供回测、事件重建与回归测试使用。
  • 时间完整性：消息保留其生产者在创建时刻报告、观测、请求或推断的内容， 可用的出处一并保留。不可变性并不证明生产者的信息为真；更正需要显式的新记录。
  • 更安全的并发：读者不必协调以防护消息载荷被后续改写，消除了共享状态周围 一类常见的竞态来源。
  • 可调试、可审计：日志、跟踪、重放工具与死信检视保留原始载荷，从而可以追查 系统收到或创建了的是什么、发生于何时，以及系统用它做了什么。
  • 清晰的所有权边界：组件把进入的消息当作输入。需要不同表示时，显式派生新的 本地状态或新消息。
  • 更稳健的分布式：序列化的消息本来就以副本跨越进程与服务边界，内存模型 沿用同一条所有权规则，与现实一致。

证据与权威​

区分外部报告、本地观测、推断与策略决策。由它们派生状态时，保留各自的出处与 不确定性。一个合法的数值或状态转换，本身并不确立某项交易场所事实。证据缺失时， 不能因为超时或重试上限到期就把它当作已确认的结果。

执行策略把这一规则应用于命令结果、对账， 以及保留历史的限度。

受控的非确定性​

让时间、随机性、输入顺序与外部影响在其消费边界处显式化。可复现的测试必须 控制影响其断言的那些来源，并保留调查失败所需的输入、种子与配置。任何确定性 保证都要写明其成立所依赖的二进制、平台与输入条件。

DST 契约定义了种子控制执行的支持范围。实时的交易场所行为 与独立的外部输入留在该保证之外。

有界的资源使用​

队列、重试、保留历史与回调链的设计要带上显式的资源预算与耗尽行为。内存用量 会波动时，除了条目数还要计入载荷大小。约束工作量而不只是存储，防止一个能 持续补充的队列独占执行。

按受影响的契约选择背压、拒绝或安全终止。过载不得静默丢失必要的状态转换， 也不得把部分应用的操作呈现为已完成。这些是设计要求。既有路径仍可能是无界的， 如实时派发与过载行为所述。

故障后的恢复​

不可恢复的故障不得让系统继续在可能无效的状态上运行。正常启动包含配置好的 状态恢复，因此重启走的就是普通启动的同一条初始化路径。恢复依赖保留的状态与 后备存储的持久性。

进程故障后的重启由外部 supervisor 负责。恢复以尽量缩短停机为目标，其时长取决于 要恢复的状态与后备存储。执行恢复必须对账交易场所状态，而不是盲目重试交易场所命令。 正常运行保留优雅关停；不可恢复的故障可能让清理不再安全。

进程与持久化边界的说明见运行时故障与恢复。

领域与集成边界​

领域类型与契约定义交易行为。组件经由显式接口与不可变消息通信。 端口与适配器把交易场所传输与后备存储实现挡在共享交易核心之外， 因此自定义集成保留同样的领域契约。

回测与实时行为​

回测、沙箱与实时环境共享核心交易组件与行为契约。同一份策略与执行算法代码 可在这些环境间运行。实时执行还会引入交易场所、传输、时序、持久化、外部活动与 对账行为，模拟未必能复现。代码共享不意味着不同的输入或运行条件会得出相同结果。

通用核心提供各引擎与接口， 行为模型定义模型实现如何进入运行时。

排队回调派发要求​

规范的 actor 与策略投递必须保持发布顺序、组件独占访问与生命周期资格， 并做到有界进展。重入不得改变排序规则。有序投递并不意味着存在按事件时间 切成的缓存快照。

运行时在一小组显式的所有权边界上掌控排空调度，时机是外层可变借用结束之后。 各个派发、flush 与生命周期方法不得各自持有排空策略。失败处理与清理交给现有的 生命周期所有者。只在能降低复杂度、又保留回测结算与实时让出规则的地方， 才共享调度代码。

同步核心与回测中的确定性回调顺序是必须满足的启用准则。要通过真实的 native 与 Python 组件验证精确序列，覆盖嵌套发布、扇出、回调生成的命令、同一时间戳的工作， 以及跨有界排空遍历的续作。仅凭最终的计数与余额无法确立顺序。

这些是排队派发的要求，不是对既有同步路径的保证。 回调派发契约规定维护时机、所有权边界、生命周期失效 与排空行为。运行时一致性契约 记录实现覆盖与尚未完成的启用要求。
