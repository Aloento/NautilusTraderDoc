执行测试规范

使用这份测试矩阵，配合 Rust 的 ExecTester 策略验证适配器的执行功能。Python 将其作为内置策略暴露，通过 nautilus_trader.testkit.ExecTesterConfig 配置；Rust 代码从 nautilus_testkit::testers 导入。用例使用带前缀的 ID（例如 TC-E01），按功能分组。

每个适配器必须通过与其支持能力相对应的那部分测试。

测试从简单（单笔市场单）到复杂（括号单、修改链、拒绝处理）递进。通过第 1-5 组的适配器即视为达到基线合规。 先用数据测试规范验证数据连通性，再跑执行测试。

适配器特有的行为（交易场所如何撮合市场单、如何处理 TIF 选项等）写在各适配器自己的指南里，不写在这里。 每个适配器指南都应包含一份能力矩阵，列出其支持的订单类型、有效期选项、动作和标志。

前置条件​

运行执行测试前：

  • 有有效 API 凭证的 demo/testnet 账户（推荐但非必需）。
  • 账户资金足以支撑测试所用的金融工具和数量的保证金。
  • 目标金融工具可用，且能通过 instrument provider 加载。
  • 已设置环境变量：{VENUE}_API_KEY、{VENUE}_API_SECRET（或 sandbox 变体）。
  • 交易场所若提供 demo/testnet 模式，使用该环境下创建的凭证。演示环境与生产环境的 API key 通常相互独立、 不可互换。用错凭证会导致鉴权错误（如 HTTP 401）。
  • 绕过风控引擎（LiveRiskEngineConfig(bypass=True)），避免干扰。
  • 启用对账以验证状态一致性。

Python 节点搭建：

使用 nautilus_trader.live.LiveNode。若需在节点构建前注册适配器客户端工厂，调用 LiveNode.builder(...)。

from nautilus_trader.common import Environment
from nautilus_trader.config import LiveExecutionEngineConfig
from nautilus_trader.config import LiveRiskEngineConfig
from nautilus_trader.live import LiveNode
from nautilus_trader.model import TraderId
from nautilus_trader.testkit import ExecTesterConfig

node = (
    LiveNode.builder("TESTER-001", TraderId("TESTER-001"), Environment.SANDBOX)
    .with_risk_engine_config(LiveRiskEngineConfig(bypass=True))
    .with_exec_engine_config(LiveExecutionEngineConfig(reconciliation=True))
    .add_exec_client(None, adapter_exec_client_factory, exec_client_config)
    .build()
)

tester_config = ExecTesterConfig(
    instrument_id=instrument_id,
    client_id=client_id,
    order_qty=order_qty,
)
node.add_builtin_strategy("ExecTester", tester_config)
# Register remaining components, then start or run

Rust 节点搭建（参考：crates/adapters/{adapter}/examples/node_exec_tester.rs）：

use nautilus_testkit::testers::{ExecTester, ExecTesterConfig};
use nautilus_trading::strategy::StrategyConfig;

let tester_config = ExecTesterConfig::builder()
    .base(StrategyConfig {
        strategy_id: Some(strategy_id),
        ..Default::default()
    })
    .instrument_id(instrument_id)
    .client_id(client_id)
    .order_qty(order_qty)
    .build()?;
let tester = ExecTester::new(tester_config);
node.add_strategy(tester)?;
node.run().await?;

时间戳量纲​

Nautilus 以 Unix 纳秒（UnixNanos）存储 ts_event 和 ts_init。所有执行消息都必须使用该量纲：订单事件、 成交、账户状态和对账报告（OrderStatusReport、FillReport、PositionStatusReport、ExecutionMassStatus）。

  • 小于 10^16 的值不可能是合法的 Unix 纳秒时间戳（10^16 ns 约为 1970-01-01 之后 116 天），通常说明适配器 没有把交易场所的量纲转换过来。
  • 转换正确的秒级交易场所时间以 000000000 结尾，仍然算通过：那是精度粗，不是量纲错误。
  • 实时流的 ts_event 应接近会话的挂钟时间。对账报告可以更久远，只要量纲是纳秒就仍然有效。
  • ts_init 是 Nautilus 创建对象时的本地时钟。交易场所时钟超前时，ts_event 略大于 ts_init 是可能的。

收到的行情或订单事件时间戳未通过量纲检查时，ExecTester 会发出警告。报告的时间戳要检查报告本身。任何执行 消息上出现量纲警告，或残留的秒、毫秒、微秒，一律按失败处理。

基本冒烟测试​

一个随时可跑的快速健全性检查，例如改动适配器之后或开发迭代之间。测试器启动时用市场单开仓，挂出一买一卖 两个 post-only 限价单，等待 30 秒后停止（撤销未决订单并平仓）。

Python 配置：

ExecTesterConfig(
    instrument_id=instrument_id,
    order_qty=Quantity.from_str("0.001"),
    open_position_on_start_qty=Decimal("0.001"),
    enable_limit_buys=True,
    enable_limit_sells=True,
    use_post_only=True,
)

Rust 配置：

ExecTesterConfig::builder()
    .base(StrategyConfig {
        strategy_id: Some(strategy_id),
        ..Default::default()
    })
    .instrument_id(instrument_id)
    .client_id(client_id)
    .order_qty(Quantity::from("0.001"))
    .open_position_on_start_qty(dec!(0.001))
    .enable_limit_buys(true)
    .enable_limit_sells(true)
    .use_post_only(true)
    .build()?

预期行为：

  1. 启动时：市场单成交，建立持仓。
  2. 在距最优买卖价 tob_offset_ticks（默认 500 个 tick）处挂出两个限价单。
  3. 策略空闲 30 秒。检查日志有无错误、被拒订单或断连。
  4. 停止时：撤销未决限价单，用市场单平仓。

通过标准：日志无错误，持仓干净地开平，限价单得到交易场所确认。

下面每组先给汇总表格，随后是详细测试卡片。 测试 ID 采用间隔编号，便于插入新用例而无需重排。

TC-E01：Market BUY - 提交并成交​

字段值
前置条件适配器已连接，金融工具已加载，行情正在流入，无未了结持仓。
操作ExecTester 通过 open_position_on_start_qty 开多头持仓。
事件序列OrderInitialized -> OrderSubmitted -> OrderAccepted -> OrderFilled。
通过标准持仓建立，side=LONG，数量与配置一致，成交价在市场范围内，AccountState 已更新。
跳过条件适配器不支持市场单。

注意事项：

  • 部分适配器把市场单模拟为激进的限价 IOC 单（见适配器指南）。
  • 无论交易场所机制如何，策略视角看到的事件序列应当一致。
  • 成交价应在最近的买卖价差之内。
  • 部分成交是合法的。核对累计成交数量与订单数量一致。

    order_qty=Quantity.from_str("0.01"),

    enable_limit_sells=False,

TC-E30：修改限价 BUY 价格​

字段值

结果不明的失败​

这些用例证明：交易场所结果未知时，适配器的请求失败不会变成终态拒绝事件。通过标准同时定义了本地准备失败的 例外：必须能确定命令未被发送，且失败可归因于某一条取消或修改命令。两个条件都成立时，适配器可以发出匹配的 拒绝事件。

通过标准：

  • 提交因传输错误、超时、WebSocket 发送失败、重试耗尽或响应解析失败而不发出 OrderRejected。
  • 取消因传输错误、超时、WebSocket 发送失败、重试耗尽或整请求服务失败而不发出 OrderCancelRejected。
  • 修改因传输错误、超时、WebSocket 发送失败、重试耗尽或整请求服务失败而不发出 OrderModifyRejected。
  • 能证明命令无法发送的本地取消准备失败，在适配器可把失败归因于单条取消命令时， 可以发出 OrderCancelRejected。
  • 能证明命令无法发送的本地修改准备失败，在适配器可把失败归因于单条修改命令时， 可以发出 OrderModifyRejected。
  • 整批请求失败且交易场所未返回逐单结果时，不逐单发出拒绝。
  • 显式的逐单交易场所拒绝仍带着交易场所原因发出对应的拒绝事件。

在交易场所更新、查询结果或对账确认解决之前，订单保持在合适的在途状态。

字段值

  • 断言失败的成交不确认、也不终态化其订单。
