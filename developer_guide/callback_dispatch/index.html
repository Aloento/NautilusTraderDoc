回调派发契约

本页定义排队（queued）的 actor 与策略回调的所有权、顺序与进展要求。策略层面的 说明见设计原则。

:::info 入队不等于已生效 这些要求是排队 actor 与策略回调投递的设计约束，不是对既有同步派发路径的保证。 支持消息总线同步重入，并不会启用排队的 actor 或策略回调。 :::

按目的阅读本页：

  • 规范性契约：顺序、可观察状态、有界进展与 排空边界设计定义了启用（activation）的要求。
  • 当前实现：实现限度与 运行时集成区分既有机制与启用缺口。 运行时一致性契约把源码与代表性检查映射到各要求。
  • 私有实现细节：派发原语、命令传输与 存储记账说明机制如何强制执行这些要求。

失败消息与纠正动作见重入与派发诊断。

回调序列示例​

这个例子演示排队的契约。生产环境的规范回调仍是同步的。假设事件 A 有两个合格 接收者——策略 S1 与 S2，事件 B 的接收者是 S3；没有无关的待处理工作，且每个排空 边界上所需访问都可用。

Publication A
  |  Reserve publication ordinal before synchronous subscribers run
  |  Admit S1(A), creating root R; admit S2(A) under the same root
  v
Callback queue: [ S1(A) | S2(A) ]                         root R
  |
  |  Enclosing runtime borrows end
  v
Safe boundary: drain callbacks
  |
  +-- S1(A) runs                                          root R
  |     |
  |     +-- publish B --> queue S3(B) after S2(A)          root R
  |     |                (no recursive S3 invocation)
  |     |
  |     +-- send C -----> command transport retains C     root R
  |                      (owner thread; context preserved)
  |
  +-- S2(A) runs                                          root R
  |
  +-- S3(B) runs                                          root R

Callback order: S1(A) --> S2(A) --> S3(B), even across bounded drain passes
Budget:         three completed deliveries charged to R,
                even across bounded drain passes

When the runtime processes C (timing depends on the runtime):
  restore R --> handle C --> any resulting callbacks retain R
                            and queue by publication/admission order
  C itself consumes no callback delivery budget

嵌套的发布 B 排在 A 的待处理接收者之后。回调与命令都保留根 R。

上述回调顺序并不规定 C 相对于 S2(A) 与 S3(B) 何时执行。回调遍历之间的命令处理 由回测结算与实时调度决定。只要 C 或其他被保留的后代 持有 R，R 就存活。让出不会重置其预算。从外部线程或无关任务发送不会自动继承 R。

术语​

术语含义
Publication（发布）一次事件发布，其序号在同步订阅者工作之前预留。
Admission（准入）在构造捕获之前预留回调计数、已知存储与队列位置。
Slot（槽位）队列中一个有序条目，无论处于预留、就绪还是已取消状态。
Capture（捕获）为回调或调用保留的所有权值。
Root（根）后代工作共享的因果所有权与累计投递记账。不回滚。
Retained work（保留工作）队列中或挂起的工作，使其根在当前调用或排空之后仍存活。
Drain（排空）按序对回调槽位的一次有界遍历。
Safe boundary（安全边界）运行时拥有的时刻：外围借用已结束，允许调用回调。

顺序与重入​

:::tip 什么是重入？ 重入指代码在其较早一次调用返回之前再次被进入。例如消息总线的订阅者又发布了 另一条消息，导致嵌套投递先于原来的发布完成。这发生在单个线程上，不需要并行执行。 :::

在同一运行时线程内，规范的 actor 与策略回调必须跨组件、跨 topic 保持 发布顺序。该规则对空闲与活跃的组件同样适用。嵌套发布不得超越更早发布的 待处理投递，包括更早发布的全部接收者。相互独立的节点之间没有共享的全局顺序保证。

回调要求其组件的独占访问，以及一个外围可变运行时借用已结束的投递边界。 native 与 Python 组件必须遵循同样的顺序契约。

原始 Python 订阅者​

原始的 Python topic 消息把原始对象同步投递给 订阅的可调用对象，包括在嵌套发布期间。它与规范的自定义数据订阅共享运行时总线 与 topic 空间。排队的顺序要求适用于规范回调，原始可调用对象保持同步。 原始可调用对象内部的嵌套发布，仍必须保持待处理规范投递的发布顺序。

维护与可观察状态​

组件维护随每个排队事件运行，在该事件的作者回调之前。包括：

  • 指标更新。
  • 定时器清理。
  • 条件单处理。

作者回调被抑制时，维护仍执行其适用的生命周期规则。维护发出的事件进入同一套 有序派发机制。

缓存状态与资格​

引擎缓存的变更与直接的门面效果保持同步。 回调观察到的是当前缓存状态。有序投递不提供按事件时间的缓存快照。不可变的 事件载荷记录着事件本身，而缓存可能已经反映了后续变化。把指标更新与事件投递 放在一起，保持了它们与相应回调之间的顺序。

例如，引擎可以应用订单更新 E1，把其回调排队，并在该回调排空之前应用 E2。 E1 的回调收到 E1 的不可变载荷，但缓存查询可能返回 E2 之后的订单状态。 关于 E1 的事实看载荷，当前运行时状态看缓存。

作者回调在事件到达与投递两个时刻都要求具备资格。停止、重置或退役不得把 旧回调带进新的注册或生命周期世代。

有界进展​

排空按序处理队列中的回调，在允许时尝试投递。待处理回调参与运行时的排空 条件。实时执行使用有界的排空批次，并在批次之间让出。回测在推进模拟时间之前 完成待处理工作。失控的回调链会产生显式故障。

队列溢出记录致命错误，并在安全边界停止执行。它既不能静默丢弃回调，也不能在 某个操作的同步效果中途打断它。已完成的效果不会被回调派发回滚。

排空边界设计​

运行时集成必须把回调排空集中在少数几个显式的所有权边界上。排空调度归运行时 所有。各个派发与 flush 方法不得各自持有自己的排空策略。这能把借用的释放、 回调顺序与失败处理保持在少数几处，并限制重复的排空调用、异步传播与错误管道。

每个边界必须指明：

  • 哪些组件、引擎与缓存借用已经结束。
  • 接下来可以运行哪些回调。
  • 失败由哪条现有生命周期路径处理。

关停与所有权清理保持在该生命周期所有者之下。回调派发不得引入平行的生命周期或 恢复状态机。失败时停止后续派发、保留错误，并按清理契约要求的顺序释放保留的 所有权。

用满足顺序、进展与所有权要求的最小边界集合。只有在外移排空仍保留这些要求时 才外移。用精确的回调序列测试验证边界的位置，包括跨有界排空遍历的续作。 仅仅减少排空位置并不能确立正确性。在同步核心与回测中，确定性的回调顺序仍是 必须满足的启用准则。

调度与所有权边界​

actor::drain_callbacks(budget) 保持为公共操作：处理一个有界批次，返回是否 仍有回调剩余或派发是否失败。回测结算与实时调度负责该操作外围的重复。 优先用这些按运行时编写的小循环，而不是带运行模式、生命周期状态或策略对象的 共享调度器。只有当共享能消除重复、又不引入那些机制时，才共享更多代码。

回测边界​

回测结算集中调度的参照，但不是"每个时间戳结束时排空一次"。定时器处理器在下一个 处理器之前结算自己的工作，即使在同一时间戳。交易场所处理在结算之前释放其借用。 把所有排空移到最外层循环会改变这些边界。启动阶段的数据命令与回调遍历也不能 使用无限制的结算，否则交易命令的执行时机就会改变。

实时启动与独立生命周期​

启动顺序​

保持启动顺序：工具事件先到达缓存，之后执行客户端才连接、订阅命令才被处理。

实时启动成功后，run_with_mode 在 trader 启动、plug-in 启动与启动期系统派发 之后，抵达首次运行循环排空，然后才选取下一条通道消息。就用这个既有边界， 除非某个已识别的生产者与顺序要求证明确需更早的排空。

连接 future 在 await 期间持有引擎的可变借用，启动对账期间的批量状态请求也是。 它们完成本身并不构成再加一个排空位置的理由。重放与启动失败走各自的出口， 需要各自的所有权证明。

独立生命周期的限制​

独立调用 LiveNode::start 与 stop 不运行连续的事件循环。start 返回时 保留 runner，stop 或 abort 会处理 runner 的待处理消息。这条路径作为测试与 嵌入的积木继续受支持，保持其现有的同步回调。finish_startup_trader 里 孤零零一次排空无法提供排队回调的续作。

LiveNode 的初始排队回调启用仅限于拥有节点事件循环的 Rust run/run_with_mode 与 Python run/run_async。经由独立 start/stop 的排队投递暂缓。在回调准入之前，启用必须先拒绝"独立启动 + 排队投递"并给出清晰错误；不得静默回退到同步投递，也不得让回调停留在未投递 状态。这一限制针对独立启动，不针对通过正在运行事件循环的节点的 handle 发出 停止请求。

排队 actor 投递与这一拒绝都尚未实现。强制执行该生命周期限制是一项启用要求， 它不改变现有的独立 API。

宿主运行的取消与遗弃​

被 await 的宿主运行取消会驱动优雅关停。而在宿主循环仍在运行时丢弃该运行， 可能在关停完成之前就 drop 掉其 future。该路径上不保证回调投递。启用覆盖必须 把遗弃之后的所有权释放与受守卫的处置清理，同优雅关停分开验证。

run future drop 时会释放报告借用，但本身不运行报告任务的取消清理，也不 flush 延后的工具更新或移除定向查询标记。

实时停止与终态清理​

LiveNode::finalize_stop 无法独自拥有回调拆除：调用方仍持有通道接收端， 且正常关停在此之后还处理缓冲事件。start/stop 路径保留其 runner，而 run_with_mode 在本地拥有接收端。终态清理的所有者是 LiveNode::dispose， 不是正常停止，也不是运行循环的末尾。

:::info 终态所有权清理 LiveNode::dispose 按此顺序执行回调清理：

  1. 处置内核。确保没有任何引擎或组件借用残留，然后才释放 runner。
  2. 释放保留的 runner 并丢弃其待处理消息，包括处置期间 stop 回调排入的队列工作。
  3. 记录任何已闭锁的回调失败，然后尝试清除回调状态。清理被拒绝要记日志， 但不强制重置。

处置不得变成又一个回调投递循环。保留正常停止与 runner 复用。不要为了让清除 成功而在正常停止或运行循环末尾关闭通道。保留 runner 的释放归处置所有。 :::

丢弃 runner 不能证明所有根都已释放。清除仍必须拒绝活动作用域或外部保留的根， 并报告失败而不强制重置。被拒绝的清除让回调状态保持原样。阻塞的所有权释放后 可以重试处置。需要验证：

  • 保留 runner 中带根的消息在处置之前阻止清除，并被处置释放。
  • stop 产生的带根消息被处置丢弃，不进行回调投递。
  • 所有权允许时，致命运行循环闭锁在处置时清除。
  • 外部所有权持续阻止清除。

必需的边界验证​

序列要求​

边界变更需要针对下列各项的精确序列断言：

  • 回测启动的数据命令与回调先于首个输入，交易命令留在队列中。
  • 实时工具处理先于执行连接，以及被启用路由所要求的任何顺序。
  • 同一时间戳的定时器与回调生成的命令，先于下一个定时器或时间推进。
  • 跨有界遍历的续作、实时停止资格，以及不变的纯通道调度。
  • 正常停止产生的工作对致命中止丢弃的区分，加上根仍存在时的清理拒绝。
  • 在回调准入之前拒绝"排队投递 + 独立实时启动"，同时保留同步的独立行为 与运行中节点经 handle 驱动的关停。

这些序列检查是启用要求，不是实时排队投递已实现的证据。要通过真实的 native 与 Python 组件走被启用的路由。仅靠私有派发器的测试，证明不了运行时借用恰好在 选定边界结束。

访问强制​

对每条被启用的路由，经由现有准入机制预留，并为调用获取受检的组件访问。 逐一识别回调能够触及的引擎、客户端与缓存访问：actor 分配守卫保护不了那些 独立的借用或未检查的句柄。实现必须在调用回调之前确立兼容的访问。仅靠成功的 actor 守卫并不充分。

待处理报告测试​

用显式的测试同步点把报告请求保持在挂起状态。走真实的回调路由，在释放报告 前后断言其精确的事件与命令序列。路由可达时，覆盖成功完成、超时、关停取消 与宿主运行遗弃。

报告挂起期间，共享的命令访问可以继续。客户端的可变访问必须等到冲突借用结束。 路由需要延后时保持发布顺序与报告 future 的进展。不要把已声明安全排空边界上 忙碌的队头变成无界重试。致命停滞投递规则仍然适用。

现有的实时节点测试覆盖报告串行化、 延后工具更新、超时与关停清理。它们不走生产环境的排队 actor 投递，不能替代 这些按路由的启用测试。

运行时集成​

根传播测试覆盖同步与实时运行时中的保留续作、 数据与交易命令，包括延后的交易子命令。实时数据与执行事件通道也在混合通道 跳转与启动缓冲中保留根。

回测​

回测在启动数据命令批次、命令与执行事件结算、定时器处理器之后调用边界排空。 每次回调遍历处理有限数量的槽位。模拟时间推进之前，只要还有回调或同步命令 待处理，结算就继续。仅有保留的根并不能让结算保持运行。启动照旧把交易命令 留在队列里，直到正常结算。

派发错误从回测执行中传播出来并触发中止清理。trader 启动失败也会停止引擎、 丢弃待处理的同步命令。中止（abort_run）、重置与处置在清除回调捕获之前先 释放同步命令批次。外部保留的工作仍可能阻止回调清理。正常结束（end_impl） 在清除派发器之前排空残余工作。

实时运行循环​

实时运行循环在选取下一个事件之前排空一个有界的回调批次，并在有回调待处理时 让出。待处理回调无需另一条通道消息即可恢复。停止信号在批次之间保持有资格。 现有的通道优先级与纯通道让出保持不变。

回调失败时：

  • 独立 runner：返回错误，不关闭通道、不丢弃其消息。
  • 实时节点：触发现有关停，跳过残余事件时间窗与最终缓冲派发。接收端 drop 时丢弃待处理的通道消息，包括 stop 回调排入的命令。

两条路径都保留致命回调闭锁，都不清除回调所有权。

启动与残余 flush 不集成回调排空。处置在尝试回调清理之前先释放自有的工作， 且不投递回调。启用仍需要为实时生命周期路径提供显式的调度与所有权覆盖， 同时不假定每个生命周期方法都需要一次排空。

实时报告 future 会跨循环迭代持有共享客户端借用。仅在循环顶部的排空，证明不了 需要客户端可变访问的回调的安全性。排队回调启用必须把这些保留的借用计算在内。

启用要求​

这些边界并不启用排队 actor 投递。启用之前，运行时集成必须：

  • 在启用更多回调路由或引入可复用的调用存储时，保持 相互独立的入口边界。
  • 完成终态处置之外的实时生命周期排空边界与所有权覆盖。
  • 在准入排队回调之前，强制执行 实时生命周期限制。
  • 为每条被启用的回调路由确立 native 与 Python 的所有权安全。
  • 经由完整的回测与实时运行时生命周期验证排队回调。
  • 在同步核心与回测中，通过 native 与 Python 组件证明确定性的回调序列。 覆盖嵌套发布、扇出、回调生成的命令、同一时间戳的工作，以及跨排空批次的 续作。仅凭最终的计数与余额无法证明顺序。

公开的交易消息及其直接的 dispatch() 路径不携带跨线程的回调上下文。 同步队列私有地拥有其上下文。实时命令通道使用下文描述的信封。仅靠运行时 排空，证明不了完整的实时生命周期集成或后端一致性。

私有派发原语​

actor 模块包含私有的访问、准入、发布、调用与存储原语。数据与交易命令在同步 与实时运行时中保留回调根。本地发出的实时数据、 执行、系统消息与时间事件经由其通道保留根。

生产环境的 actor 查找、组件访问与消息总线路由都不使用排队回调投递。要启用 该投递，运行时边界需要 native 与 Python 的所有权支持。仅靠原语与运行时排空 证明不了运行时所有权安全，也证明不了 native、direct 与 dynamic 回调的一致性。

发布与准入​

发布作用域在同步订阅者运行之前预留一个序号（ordinal）。回调预留按发布 序号排序，再按准入序号排序，因此嵌套发布排在其外围发布的每个待处理接收者之后。

作用域按栈顺序嵌套与 drop。drop 一个作用域会恢复发布状态而不投递回调。 发布过程中的 unwind 会闭锁一个致命错误。

publish_any 与共享的类型化发布路径在进入总线 tap 与同步订阅者运行之前进入 作用域。try_publish_any 在初始的总线访问检查之后做同样的事。作用域在嵌套 的类型化与 Any 发布之间保持预留顺序。经由这些路径 unwind 会闭锁致命派发 错误，即使没有回调被排队、或调用方随后捕获了 panic。

发布作用域给预留排序，但不准入规范回调，也不排空它们。

准入在调用方构造所有权捕获之前预留计数、已知存储与队列槽位：

  • 成功的预留接受其捕获，即使另一个操作随后闭锁了失败。
  • 未完成的预留会阻塞后续投递与拆除。
  • 取消留下一个槽位，由显式排空或拆除释放。
  • actor 预留保留注册身份，因此替换或重新注册同一分配会跳过过期的处理器。 被跳过的投递仍按完成计入其根的预算。

排空与进展​

一次排空最多处理它得到的槽位预算，包括已取消的槽位。队列的第一个回调 无法获得其组件的独占访问时，队列处于忙碌队头状态，这会阻塞后续投递。

私有边界排空在显式排空之上加了更严格的契约：调用方必须确立一个安全的投递 时刻。

显式排空的结果含义边界排空的行为
队列为空没有剩余槽位正常返回
槽位预算耗尽遍历之后仍有槽位剩余正常返回。不算停滞
进入被延后发布、递归排空、拆除或受检访问阻止进入报告有活跃工作。不闭锁失败
未完成的队头预留第一个预留还没有捕获报告有活跃工作。不闭锁失败
忙碌队头组件独占访问不可用闭锁致命的停滞投递错误

进入被延后时不做任何工作。未完成的队头预留或忙碌队头，可能出现在同一次遍历 已有若干投递完成之后。**错误结果不返回投递计数。**边界上的忙碌队头是致命的， 即使前面的回调已经取得进展。耗尽槽位预算（包括耗在已取消槽位上）不是停滞投递。

队列为空并不意味着所有保留的根都已释放。仅凭所有权记账不是继续排空的理由。 边界排空保留第一个致命错误，并把队列中的捕获留到显式拆除时再释放其所有权。

:::warning 排空前先释放外围借用 守卫的销毁只释放访问，不排空回调。调用方还必须在排空之前结束外围的引擎、 缓存及其他未跟踪的借用。 :::

unwind 期间的排空​

在 panic unwind 期间进入的、本来会成功的排空，在退出时闭锁致命的投递失败， 即使其队列为空。它返回的结果仍是成功的。该失败可通过回调失败检查获知， 并会停止下一次边界排空。

回调根与预算​

根拥有一个进入的发布或预留的投递预算，以及它引发的全部回调工作。 发布顺序不依赖于工作归哪个根所有。

  • 嵌套的发布与预留继承活动中的根。
  • 没有活动根的发布，在其首次回调准入或命令发送时启动一个根。 空作用域不分配根。
  • 发布作用域之外，若尚无活动根，每次准入各自启动一个根。

投递预算对槽位预算​

每次完成的投递按其根的预算计费一次。忙碌的尝试与已取消的槽位不计费， 尽管已取消的槽位仍消耗排空的槽位预算。

到达链路上限时，派发在运行下一个就绪回调之前闭锁致命的失控错误。 被阻塞的回调留在队列中等待显式拆除。致命错误会停掉整个派发器， 尽管各根有各自独立的预算。

保留工作与清理​

队列槽位、活动作用域与保留的调用工作都让其根存活。**队列为空不会重置 幸存根的预算。**保留的存储捕获当前活动的根，没有活动根时启动一个。 该存储增长时保留其根。

恢复与存储复用​

经由 with_chain 恢复保留的工作，会让其根在该调用期间变为活动。返回或 unwind 时恢复外围的根。调用批次对每个保留的值使用该机制。恢复工作本身 不算一次投递。每个调用批次局部于一次准备与调用；其底层分配不决定后续 值的根——每个值捕获其自身准入时刻活动的上下文。

相互独立的定时器触发​

回调注册与因果所有权有各自的生命周期。复用已注册的定时器回调不会复用 某次触发的预算。每个独立的实时时间事件信封都在回调查找与调用之前建立 自己的作用域，即使投递发生在另一个活动作用域内部。保留的续作保持其 原始根。仅靠存储复用不会让无关事件变成续作。

销毁与释放​

已投递捕获的析构函数在该投递的根活动状态下运行，包括 unwind 期间。 未被调用的批内值销毁时同样恢复其根。

根及其存储的计费在最后一个所有者 drop 时释放。取消、失败的批次与显式 拆除使用与其他保留存储相同的所有权清理。保留的工作在释放之前阻止拆除。

失败清理​

溢出闭锁第一个致命失败，并在不构造捕获的情况下拒绝后续预留。同步的门面 效果可以在运行时于安全边界报告失败之前完成。队列槽位仍为所有权保留， 等待显式拆除。失败的调用批次在准备退出、其守卫释放之后释放捕获。

拆除顺序是强制的：

  1. 在清除重置闭锁之前报告致命错误。这是调用方的责任。
  2. 拆除开始之前结束所有活动的发布、预留、调用、链、排空与访问作用域。 清除会拒绝活动作用域与外部保留的根。
  3. 先摘除存储，再释放捕获。
  4. 释放捕获。

拆除在整个清除期间拒绝由析构函数驱动的准入。

准备与析构安全​

调用准备把批次所有者留在获取守卫的调用之外。被拒绝或 unwind 时，先前 转移的捕获会存活到那些守卫释放。调用方在构造每个捕获之前预留，并在该 调用内部获取准备守卫。原语管不了作者代码持有借用期间构造或显式销毁的 任意局部变量。析构函数不得在既有 unwind 期间 panic。

重入与派发诊断​

组件访问冲突​

受检的组件状态访问失败时， ComponentAccessError 会描述资源与尝试的操作。这些诊断已经适用于同步路径，并不代表排队投递已启用。 冲突可能来自回调重入，也可能来自一个持有过久的普通借用。消息不会指明持有者 及其调用栈。

变体消息前缀含义与动作
NotRegisteredCannot access {resource} during {operation}: the actor is not registered注册尚未提供该资源。访问前先注册组件。
ReadConflictCannot read {resource} during {operation}: it is already mutably borrowed读取之前先释放已有的独占借用。
WriteConflictCannot modify {resource} during {operation}: it is already borrowed修改之前先释放已有的共享或独占借用。

native 的 try_cache_ref() 与 try_clock_mut() 返回这些错误。对应的 cache_ref() 与 clock_mut() 带同样的诊断 panic。见 native 访问方法。

可移植的 Rust 门面同样报告访问冲突：

  • CacheApi 不可失败的读方法带 ReadConflict 与操作名 cache read 的诊断 panic。 get() 经 anyhow::Result 返回该冲突，操作名为 get。可失败的 try_* 查找经查找错误的 Access 变体返回它，操作名是方法名，如 try_position。
  • ClockApi 在 native 支撑下，冲突的读带 ReadConflict panic。定时器与告警的设置方法 经 anyhow::Result 返回 WriteConflict；cancel_timer() 与 cancel_timers() 在该冲突上 panic。时钟的诊断会点明尝试的方法。 由处理器支撑的时钟委托给其处理器，而不是这些 native 借用检查。

Python actor 的信号订阅与退订，会把冲突的 actor 借用映射为 RuntimeError， 资源名为 Python actor，操作名为 subscribe_signal 或 unsubscribe_signal。这并未覆盖所有 Python 或 native 的访问路径。

诊断冲突的方法：

  1. 在 traceback 中定位被尝试的操作。
  2. 沿着外围借用追溯，穿过任何同步发布、命令派发或生命周期调用。
  3. 在代码能重入同一资源之前结束该借用。native 代码中，用一个短作用域读取或 复制所需状态，释放守卫，然后再发布或派发。

不要绕过借用检查，也不要在冲突作用域仍活动时反复重试。移动回调排空需要 排空边界设计中的所有权与序列证明。

组件生命周期注册表操作另有独立的拒绝机制，重叠访问时报 Component '{id}' is already mutably borrowed。这一基于 ID 的检查与资源借用、 私有的回调分配守卫都不同。三者都证明不了未检查访问的安全性。

回调派发器失败​

CallbackDispatchError 暴露下列诊断。InvalidDestination、Stalled 与 Runaway 描述排队投递的 失败。当前生产路由不准入那些回调，因此这几个变体仍是私有集成与测试行为。 其他诊断在排队 actor 投递未启用时，就可能经由发布作用域、命令根记账、运行时 排空或清理出现。

派发器保留第一个致命失败。后续边界排空会报告它而不投递更多回调。已完成的 同步效果与回调效果都不回滚。

变体消息含义与动作
OverflowCallback storage limit exceeded回调准入、保留存储或命令根分配超出容量。检查捕获与保留的工作。
InvalidDestinationInvalid callback destination受检的 actor 投递发现类型不匹配。核对已注册的 actor 类型与处理器目标。
SequenceExhaustedCallback publication sequence exhausted顺序计数器无法前进。停止派发并按拆除流程处理。
PublicationUnwoundCallback publication unwound发布作用域发生 unwind。检查原始 panic，即使调用方捕获了它。
DeliveryUnwoundCallback delivery unwound排空作用域在 unwind 期间退出。检查原始 panic。
RunawayCallback chain delivery limit exceeded单个根耗尽累计投递预算。检查回调与命令之间的反馈回路。
StalledCallback delivery stalled at a safe boundary队头在已声明的安全边界上无法运行。纠正访问所有权或边界位置。
ActiveCallback work or access is still active排空进入、未完成的预留或拆除所有权阻止该操作。释放阻塞的作用域或保留的根。

Active 是一次操作拒绝，本身不闭锁致命失败。实时运行循环遇到这一排空错误 仍会退出；节点若在运行会发起关停。安全边界上的忙碌队头确实会闭锁 Stalled。 反复排空不是恢复策略。未完成的预留可能在前面若干回调已运行之后拒绝排空， 且错误结果不携带投递计数。

在走失败清理之前保留原始失败。实时处置期间， Callback dispatch failed before disposal cleanup: ... 报告既有的闭锁， Failed to clear callback dispatch during disposal: ... 报告清理被拒绝。 外部保留的工作先释放，再重试处置。不要强制清除所有权，也不要把清理当作回滚。

同步命令​

命令的祖先关系取决于发送时刻的上下文：

  • 有活动根时，命令捕获它，包括在回调投递与保留工作恢复期间。
  • 处于发布或命令处理作用域内时，发送会在需要时启动该作用域的根。
  • 在这些作用域之外且没有活动根时，发送不带根。处理它时，在首次准入回调工作 或发送嵌套命令时创建一个独立的根。

同一次排空批次中的命令，不会因为一起运行就共享一个根。处理与销毁在返回或 unwind 时恢复外围的根。

批次与子命令顺序​

一次命令排空按序处理进入时收集的批次。处理器经由同步发送端排入的命令， 留到下一次排空。交易处理器也可以捕获延后的子命令：它们深度优先执行， 按捕获顺序，先于所收集批次中的下一条命令。每个子命令捕获其捕获时刻活动的 根（包括临时的嵌套上下文），而不是在父处理器返回后改用父上下文。 端点的直接路由保持不变。

队列与派发栈帧的借用处理器运行之前、被遗弃的命令销毁之前都会结束。命令处理 不算回调投递，也不会自动排空回调。

Panic 与溢出​

处理器 panic 时，panic 向外传播。所收集批次中未处理的命令与待处理的延后 子命令，在各自的上下文下销毁。新排入的命令留在队列里。捕获的根让回调记账 保持存活，并在这些命令释放之前阻止显式的派发器拆除。被遗弃的命令也在线程 拆除时释放其捕获的所有权。

回调存储限制不会拒绝命令发送。若某次发送需要根、而其分配超出这些限制， 会在命令仍在队列中时闭锁回调溢出。命令条目不消耗回调保留单元限制，命令 载荷与队列容量也不计入已知回调存储。每个根的分配只计费一次。

:::warning 命令传输不是回调预算 这些限制不约束命令队列内存，也不约束只生成命令的循环。 :::

实时命令与事件通道​

实时数据与交易命令的发送端只在构造它的那个线程上捕获根。发送端必须在运行时 线程上构造。来自其他线程的发送属于独立入口，即使另一个运行时在那边有活动根。 派发信封携带 send-safe 的令牌。回调根与记账保持线程局部。在另一个线程上处理 带根的信封会在派发之前 panic。

派发与缓冲​

信封经由启动缓冲、runner 轮询与关停排空保留其祖先关系。交易子命令捕获自己 活动的根，保持深度优先顺序。在节点轮询的命令路径上，执行观察者在每次匹配的 端点派发之前运行，子命令亦然。处理不带根的信封会启动一个独立的惰性根作用域， 这不启用排队回调，也不自动排空它们。

启动缓冲在把执行批次拆成单笔订单时，保留每个事件的根。相互独立的批次保持 独立，直到派发。报告仍在缓冲的订单事件之前排空，账户事件仍立即处理。节点执行 观察与成交簿记在收到事件的上下文下运行。事件传输本身不消耗回调投递预算。

发送端类型与入口​

实时数据、执行与系统事件的发送端使用 EventSender<T>（DispatchSender<T> 的别名），与命令共用同一种 DispatchMessage<T> 信封。系统命令与时间事件 也使用该发送端。运行时绑定确立所有者线程。在该线程上同步发出的事件继承活动 根；外部线程的发送与无活动作用域的发送保持独立。上下文不会跨任意 spawn 的 任务或 await 点传播。

系统与时间事件​

系统事件与命令经由启动缓冲、轮询与关停保留其信封。时间事件投递在解析并调用 回调之前恢复信封上下文。定时器注册不捕获根：定时触发独立进入，复用回调不会 在各次触发之间共享预算。从活动回调作用域同步发出的时间事件则继承该作用域。 回调租约、取消与清理保持既有行为。回调传输本身不消耗投递预算。

独立发送端​

独立客户端可以把普通的 Tokio sender 转成 EventSender<T>，以保留直接的 领域事件接收端。该模式不携带回调上下文，实时 runner 的通道绑定也不使用它。 事件载荷与通道容量留在回调存储记账之外，命令载荷与队列同样如此。

跨线程销毁​

销毁线程载荷上下文根释放
所有者线程销毁其载荷时恢复该消息的根在所有者线程上释放所有权
外部线程无法恢复所有者线程的上下文经由清理队列释放令牌，不访问所有者的根

所有者在其下一次通道捕获或派发、回调静止检查或派发器清除时，收回外部线程的 释放。线程拆除也会释放它们。派发信封、线程局部上下文注册表容量与清理队列 存储都留在回调存储限制之外。

存储限制​

私有限制是：

  • 保留单元：最多 65,536。调用捕获与批容量预留和队列中的回调共享该计数， 因此计数可能保守地高于回调数量。
  • 已知存储：最多 64 MiB。
  • 回调链：每个根最多 1,048,576 次完成的投递。

这些限制是防御性的保险丝，不是负载规模的建议值。它们阻止过度的保留或回调链， 并不确立可持续的事件速率或安全的进程内存预算。限制是内部的，不对外提供配置。

计入的存储​

已知存储包括：

  • 回调值、队列槽位与可见的队列容量。
  • 链分配与调用向量的容量。
  • 调用方提供的堆开销计费。

载荷测量覆盖可访问的字符串与向量容量、递归的 JSON 内容、元数据条目、 订单事件集合、可见的订单簿条目与期权链条目。启用 defi 时，还覆盖直接 所有的区块链字符串。

共享的载荷存储可能被计费多次。数据类型名、topic 与标识符暴露字符串切片， 因此它们的计费按长度计，不含无法访问的空余容量。投递在途以及批次保留捕获 期间，计费一直保持。

:::warning 不是全进程内存上限 这份记账不是进程总内存的界。它不包括：

  • 分配器自身的管理开销。
  • 容量未被这些测量暴露的集合内部结构。
  • 驻留池存储与已注册的 actor 分配。
  • 不透明的自定义数据载荷。
  • Python 对象图与动态模块存储。 :::

调用方必须为其捕获类型提供已知的堆开销计费。泛型预留无法检查任意的所有权字段。

后端兼容性​

私有的分配守卫拒绝重叠的受检访问。**未检查的访问与外围的引擎/缓存借用 仍在这些守卫之外。**native、Python 与 dynamic 后端之间的一致性尚未确立。

direct 与 dynamic 后端必须保持同样的回调顺序、组件独占访问与生命周期资格 要求。门面效果保持同步。plug-in 边界规则适用于 跨越动态库边界的所有值。回调派发不会隐式跨该边界转移分配的所有权。

准入票据与清理作用域始终是框架机制。作者字段、回调签名与规范的门面 API 都不暴露它们。
